# 마이그레이션 규칙

> 상시 로드(`paths:` 없음) — **어기면 스키마가 깨지고 되돌리기 어렵다.** 조건부로 두면 `paths:` 를 스택 실경로로 치환해야 살아나서 «치환을 잊으면 조용히 죽는» 함정까지 생긴다(근거 `_reference/rules-loading.md`).

- 이 repo 의 마이그레이션 폴더 = `{마이그레이션 폴더}`(킷 도입 시 실경로로 치환 — 아래 명령의 같은 자리도 이 값). 도구 기본 위치와 다를 수 있다(Prisma 다중 파일 스키마 = `prisma/schema/migrations`). **새 마이그레이션은 여기에만** 만들고, 치환이 안 돼 있으면 짐작하지 말고 공백으로 보고하라.
  - 엉뚱한 폴더에 만들면 `migrate deploy` 가 «적용할 것 없음»처럼 조용히 지나가고 미추적 폴더로만 드러난다.
- 이름 = `YYYYMMDD_HHMMSS_설명<마이그레이션 꼬리>` — 꼬리는 설치 값이다(킷 README 사용법 2단계가 치환: 파일형 도구 = `.sql`·`.ts` 등 / 폴더형(Prisma) = `/migration.sql`). 치환이 안 돼 있으면 짐작하지 말고 공백으로 보고하라. **초 단위 필수**(분 단위는 병렬 작업 때 충돌). 같은 초면 사전순이 적용 순서.
- **형식은 치환 시점에 도구 기본과 맞춰라** — Prisma `migrate dev` 는 구분 `_` 없는 `YYYYMMDDHHMMSS_` 로 만든다. 규칙 형식이 도구와 다르면 생성물이 기존 것보다 앞서 정렬돼(`0` < `_`) «최신 뒤로»가 조용히 깨진다.
  - 이미 다른 형식으로 굳은 repo면(머지된 마이그레이션은 불변이라 전환 불가) 도구 생성 **직후 규칙 형식으로 rename**(적용 전이면 폴더명만 · 적용했으면 `_prisma_migrations` 메타도)하고 `ls | sort | tail -3` 으로 내 것이 맨 뒤인지 눈으로 확인한다.
- 기존 스키마에서 마이그레이션을 «뽑아내는» 명령(`prisma migrate diff` 류 — 명령 이름은 스택 치환)의 함정 3개:
  ①**섀도 DB 자리에 실 DB 를 넘기면 그 DB 가 비워진다** — 매번 DROP/CREATE 한 별도 빈 DB 만: `docker compose exec {db서비스} psql -U {user} -c 'DROP DATABASE IF EXISTS {앱DB}_shadow' -c 'CREATE DATABASE {앱DB}_shadow'`(이름은 **실 DB 와 반드시 다르게**) → `--shadow-database-url` 에 그 DB 의 호스트용 URL. 쓸 때마다 다시 돌려라.
  ②폴더는 diff 출력을 본 뒤에 만들어라 — 빈 폴더가 먼저 있으면 «이미 적용됨»으로 읽혀 빈 스크립트가 나온다
  ③도구 시각은 UTC — rename 때 현지 시각으로 고치지 마라(순서만 중요). 단 정렬이 우선: 그 UTC 이름이 main 최신 마이그레이션 이름보다 앞에 정렬되면 최신 뒤에 오는 시각으로 붙인다(UTC·현지 통일은 배포처 결정). **rename 은 적용 전에만**(적용 뒤면 체크섬 불일치 → 리셋 요구).
- 호스트에서 도구를 돌릴 땐 컨테이너 호스트명(`db:5432` 류)을 못 쓴다(Prisma `P1012`) — 그 실행에만 호스트용 URL 을 앞에 붙여라. 값의 정본은 **그 repo 가 정한 곳**(CLAUDE.md '실행·테스트' 또는 `.env.example`)이고 두 곳에 중복 기재하지 마라(포트가 바뀌면 갈린다).
  - 도구는 **`npx` 말고 로컬 바이너리로** 불러라(`node_modules/.bin/prisma` 류) — `node_modules` 없는 새 워크트리에서 `npx` 는 최신 판(RC)을 받거나 전역 CLI 에 가로채여 «No command registered for `migrate`/`generate`» 같은 엉뚱한 오류가 난다. 없으면 `npm ci` 부터.
- **"파일만 만든다"는 옵션(`--create-only` 류)도 DB 에 적용될 수 있다** — 생성 직후 적용 이력 테이블(`_prisma_migrations` 등)로 미적용을 확인하라. 이미 적용됐으면 폴더를 지우지 말고 그 상태로 진행한다(지우면 이력만 남아 다음 실행이 깨진다).
- **main 에 머지된 마이그레이션 파일은 수정·삭제 금지(불변).** 고칠 것도 새 파일로.
- 불변 파일(SQL 주석 등)엔 ADR 번호 말고 **카드 번호를 적어라** — ADR 번호는 머지 순서로 바뀔 수 있고 머지 뒤엔 그 주석을 못 고쳐 영영 엉뚱한 ADR 을 가리킨다.
- 적용 이력을 조회하려는데 `.env` 를 못 읽으면(`.env.example` 은 읽혀도 DB명이 실제와 다를 수 있다) **컨테이너에 직접 물어라**: `docker compose exec {db서비스} psql -U {user} -l`. 짐작한 DB명은 «미적용»이 아니라 «빈 결과»를 준다.
- 머지 전이라도 **이미 로컬에 적용한 파일을 «고치기»는 로컬 재적용까지가 한 작업이다** — 파일만 고치면 체크섬이 어긋나 다음 카드에서 도구가 리셋을 강제한다(로컬만 깨지고 main 은 정상이라 원인이 안 보인다).
  - **리셋은 파괴적이라 사람이 실행한다**(AI 대행 금지 — 아래 선언형 스키마 충돌 뒤 리셋도 같다). 리셋 전에 «되돌리는 내용의 새 마이그레이션»으로 풀리는지 먼저 보라.
  - 리셋 요구를 받으면 먼저 **«실제 차이가 있나»를 재라** — 0 이면 리셋 없이 체크섬만 맞추면 된다(흔한 경우: 남이 머지 «전»에 주석 한 줄만 고친 파일을 내가 옛 판으로 먼저 적용해 둔 것 — 불변 위반 아님). 우회로(`migrate diff` → 손 SQL → `deploy`)로만 풀면 어긋난 행이 남아 다음 카드가 같은 우회로를 또 탄다.
    ①재기: `node_modules/.bin/prisma migrate diff --from-migrations {마이그레이션 폴더} --to-url {로컬 DB 호스트용 URL} --shadow-database-url {섀도 URL} --exit-code` — 0 = 차이 없음 · 2 = 있음 · 1 = 실패(Prisma 6.19 `--help` 기준)
    ②**0 일 때만** `sha256sum {폴더}/{이름}/migration.sql`(mac `shasum -a 256`) 값으로 `UPDATE _prisma_migrations SET checksum='{해시}' WHERE migration_name='{이름}'` ③막혔던 명령을 다시 돌려 리셋 요구가 사라졌는지 본다.
    **2·1 이면 하지 마라** — 진짜 스키마 차이를 가린다(되돌리는 새 마이그레이션 → 안 되면 사람이 리셋).
- 되돌리기는 down 이 아니라 **«되돌리는 내용의 새 마이그레이션»**(forward-only). 머지커밋 revert 는 머지된 마이그레이션 파일을 **지운다**(불변 위반 — `mr-checks` 잡의 `migration-immutable` 이 차단) — 절차 `_reference/revert.md` B(Prisma 예시 — 경로·역DDL 은 스택 것으로 치환).
- **전역 직렬 자산**(모듈 소유로 못 막는다): 머지는 생성 순서대로. 내 브랜치가 뒤처진 새 마이그레이션이 main 에 들어왔으면 내 것을 최신 뒤로 재생성(왜·벤더 경고 `_reference/schema-conflicts.md`).
- 날짜를 «하루» 단위로 자를 땐 **현지 시각(KST) 기준** — SQL `::date`·TS `toISOString().slice(0,10)` 은 UTC 라 오전 9시 이전이 전날로 밀린다(TS·SQL 두 층에서 따로 난다).
- 제약이 걸린 테이블·enum 을 다시 만들면 **그 제약의 재생성을 함께 써라** — 겹침 차단(EXCLUDE)·CHECK·유니크를 빠뜨리면 DB 원천 보장이 조용히 사라진다(앱은 멀쩡해 보인다).
- **착수 공지 = 조건부**: 동시 작업 충돌을 직접 확인하는 것으로 공지를 대신한다(무조건 공지를 요구하면 실행과 규칙이 갈려 그 게이트가 형식이 된다).
  - 착수 전 **둘 다** 확인: ①`git fetch origin -q` 후 main 최신 마이그레이션이 내 base 보다 앞서 있지 않다 ②열린 MR 중 마이그레이션 경로를 건드리는 것이 없다(`glab api "projects/:id/merge_requests?state=opened"` → 각 iid `.../changes`).
  - 둘 다 깨끗하면 공지 없이 착수하고 **확인 결과를 카드에 한 줄**(무엇을 조회해 무엇이 없었나 — 공지를 대신하는 기록).
  - **하나라도 걸리거나 조회 자체가 실패하면 공지한다**(모르는 상태는 «깨끗»이 아니다) — 멈추고 사용자에게 문구를 건네라.
  - 공용 테이블 이름변경·삭제 공지는 이 완화 대상이 아니다(순서 문제가 아니라 남의 코드를 깨뜨리는 문제).
- **선언형 스키마 파일**(Prisma `schema.prisma`·Drizzle 등 한 파일에 여러 모듈)은 package-lock 처럼 동시 편집 충돌 자산: 충돌 시 양쪽 정의를 합친 뒤 도구 검증(`prisma validate`), 잦으면 모듈별 파일 분리. 충돌 뒤 리셋 요구 = 파괴적이라 **사람이 실행**(AI 대행 금지 · 상세 `_reference/schema-conflicts.md`).
  - 포매터가 그 자산을 통째로 재정렬한다(`prisma format` 류 — 내 파일 하나 고쳤는데 남의 모듈이 diff 에 올라온다). **format 뒤 `git diff --numstat` 로 내 파일만 남았는지 확인**하고, 추가·삭제 줄 수가 같은 순수 정렬이면 되돌려라.
- 자기 모듈 테이블은 자유(추가 위주). **공용 테이블(users 등)의 이름변경·삭제는 확장→이전→축소 3단계 + 채팅 공지.**
- 스키마 변경 MR 에는 해당 모듈 시드(멱등: 있으면 갱신·없으면 생성) 갱신을 같이 포함한다.
  - 새 모듈 시드는 본보기 시드의 게이트 관용구를 베껴라 — 기본 데이터 밖 **표본 데이터는 게이트 변수(예: `SEED_SAMPLE`) 뒤에**(안 걸면 로컬은 통과하고 머지 CI 에서야 걸린다).
  - 표본이 아닌 **기준 표**(게이트를 꺼도 행이 있어야 하는 표)를 새로 심으면 게이트 검사 스크립트의 «기준 표 목록»(`{시드 게이트 검사 스크립트}`·`{기준 표 목록}` — 스택 치환)에 등록하라 — 안 하면 머지 CI 에서야 걸린다.
