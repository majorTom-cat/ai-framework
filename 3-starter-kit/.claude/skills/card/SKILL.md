# /card — "$ARGUMENTS" 카드 등록

> **계약** · 입력: 한 줄 요약 또는 docs 경로(분해) · 산출물: GitLab 카드 생성(번호 반환)+라벨 · 검증: 보드에 카드 뜸

> **예시**: `/card 게시판 목록에 정렬 추가` · `/card docs/03_Requirement/게시판.md 분해` (문서 경로를 주면 여러 카드로 분해)

**목적**: 카드 없이 코드를 고치면 무슨 일이 왜 있었는지 아무도 모른다. 이 스킬은 그 진입 장벽을 1분으로 낮춘다.
(요구사항이 *바뀌거나 없어진* 경우는 이 스킬이 아니라 `/change` — 영향 분석·기존 카드 정리까지 필요하다)

0. **중복 확인 (등록 전)**: `glab issue list --search "{핵심 키워드}"` 로 유사 카드가 이미 있는지 본다 — 있으면 새로 만들지 말고 **그 카드에 댓글·본문 수정으로 합쳐라**(중복 카드 = 중복 구현·스펙 분기의 시작). 분해 등록이면 배치 전체에 대해 1회.
1. 한 줄 요약에서 **유형**을 판별:
   - 버그 / 기능·개선 / 리팩토링 / 인터페이스 요청(남의 모듈에 함수 노출) / 플래그 제거
   - **문서 요청**(기획자 앞 — 필요한 요구사항·시안이 무엇이고 어느 폴더로 올릴지 본문에 명시, 기획자를 담당자로)
   - **시안 요청**(개발자 앞 — 기획자가 "이 화면 후보 보고 싶다"고 발주; 담당 = 그 화면 모듈 소유자, 미정이면 공통 개발자; 처리 = `/ui 시안 {화면}` — 후보 발행(머지) 시 이 카드는 닫히고, 고르는 **시안 선택 카드**[체크박스]는 `/ui`가 별도 발행한다)
   - **docs 요구사항 분해**(문서 경로를 받으면 반나절~이틀 크기 카드 여러 장으로 쪼개 초안 제시 → 확인 후 일괄 등록)
   - **고위험 판정**: 인증·인가·세션·비밀값 / 결제·과금성 / DB 마이그레이션 / shared 승격 / 라우팅·설정·lockfile 핫스팟을 건드릴 카드면 `고위험` 라벨을 함께 단다(머지 시 AI 경고 리뷰 + 증적 3종이 필요해진다 — CLAUDE.md '머지 등급'). 애매하면 고위험으로.
2. `.gitlab/issue_templates/카드.md` 양식대로 본문을 작성한다:
   - **현재 상태·문제 서술은 코드 실물을 열어 확인하고 쓴다** — 기억·추측·"보통 이렇더라"로 적지 마라. **확인 못 한 항목은 `(미확인)`으로 표시**하고 그대로 등록하라(파일럿 2026-07-29 실측: 코드 확인 없이 쓴 "현재 상태" 3항목이 틀렸다 — 틀린 현재 상태는 엉뚱한 방향의 구현·중복 작업을 부른다). 관련 파일을 Grep/Read로 짚고, 근거 경로를 본문에 남겨라
   - **정본 참조**: `docs/` 를 **grep으로** 검색해 관련 요구사항·시안 경로를 찾아 링크(전체를 읽지 말고 관련 파일·절만). 없으면 `없음 — docs 반영 필요 여부 확인` 이라고 적는다 (지어내지 마라)
     ★**찾은 절이 전부인지 흩어짐만 확인한다**(읽으라는 게 아니다 — grep만): 같은 요구가 요구서·공통기반·해당 모듈 업무설계·관련 ADR에 흩어져 있을 수 있다. 한 절만 링크했으면 "다른 곳엔 없음" 근거를 한 줄 적어라 — 카드가 좁으면 /dev·/done 전 과정이 좁은 채 초록이 된다(bnsone #63 실측: 6건인 줄 알았던 인증 요구가 전수조사에서 30건+)
   - **수용 기준**: 각 항목을 **`- [ ]` 체크박스**로 쓰고 〔검수확인〕(화면에서 보이는 것) / 〔CI확인〕(테스트로만 검증) 태그를 붙인다 — 체크박스여야 카드 목록에 `N/M` 진척이 뜨고, **완료 시 `[x]` 갱신이 곧 완료 증거**가 된다(갱신 책임은 `/done`).
     ★수용 기준은 **구현자가 통과/실패를 기계로 판정할 수 있을 만큼 구체적**이어야 한다("잘 되게" 금지) — 〔CI확인〕 항목은 나중에 실제 테스트 1개로 물화된다(스펙-구현 어긋남을 사람 없이 잡는 유일한 방법)
   - **★품질 게이트**: 수용 기준이 모호해 "무엇이 완료인지" 판정 불가면 카드를 등록만 하고 **`대기(불명확)` 라벨**을 달아 착수를 막아라(모호한 카드는 'CI는 통과하는데 요구와 다른' 코드가 된다 — 우리 최대 사각). 작성자에게 무엇을 명확히 해야 하는지 되물어라
   - **의존**: 선행 카드 번호 또는 "없음"
   - **검수 배정**: 카드에 "검수: @누구"를 정한다(전담 검수자는 없다). **기본 = 카드 담당자(구현자)** — 만든 사람이 배포 화면을 직접 보고 확답한다. 화면·UX 위주 카드면 비개발자(기획) 검수가 적합하다고 제안하되, **다른 사람 지정은 선택이다**
     — ★**공란이거나 구현 예정자와 같다는 이유로 등록을 막지 마라**(옛 규칙 — 폐기). 막는 것은 "같은 사람"이 아니라 **"사람이 안 본 것"**이고, 그건 /todo 검수 경로가 강제한다(확답 없는 close 금지)
     — 작성자와 구현자가 다르면 검수요청 때 **작성자도 멘션**되므로 기대와 다르면 반려할 여지가 남는다(/done 9단계). 예외: 화면 없는 카드는 "검수: 셀프완료 예정"으로 명기
   - **검수 방법**: 플래그 뒤 기능이면 필수
   - **검수 상태 셋업**: 검수할 상태(데이터 N건 등)를 화면에서 어떻게 만드는지 — 못 만들면 "셋업 요청" 표기
   - 인터페이스 요청이면: **원하는 함수 이름과 입출력(시그니처)** 을 본문에 명시 (`getUserSummary(userId) → {name, dept}` 형태)
3. 위 필드를 **채울 수 없는 것만 사용자에게 질문**한다. **다 채워져도 등록 직전 미리보기(제목·수용 기준·라벨·담당·검수)를 보여주고 사용자 OK 후 등록한다**(CLAUDE.md '남기기 전 미리보기' 공통 규칙)
   — **크기 판정을 카드에 표시**: 반나절 미만이면 "크기: 작은 수정(/fix)", 그 이상이면 "크기: 보통(/dev)". 이틀을 넘어 보이면 **쪼개서 여러 장** 제안
4. **분해(여러 장) 등록이면 — 등록하기 전에 검증 3가지**(등록 후엔 위상순을 못 고친다):
   - ①**절→카드 매핑 표** — 문서의 모든 절이 어느 카드에 갔는지(안 간 절은 "이번 범위 밖"으로 명시, 조용한 누락 금지)
   - ②**의존 닫힘** — 각 카드의 선행이 기존 카드나 이번 발행분 안에 있는지(없으면 그 선행 카드부터 추가)
   - ③**위상순 등록 계획** — 선행 카드를 먼저 등록하도록 순서를 정해 의존이 항상 앞 번호를 가리키게.
5. 등록 — **여러 줄 본문을 `-d`/`--description`에 직접 넘기지 마라**(`.claude/rules/gitlab-cli.md` 정본: 개행에서 인자가 쪼개져 `Accepts 1 arg(s)`로 실패한다). **본문을 임시 파일로 쓴 뒤**(Write — `docs/inbox/_tmp/card-{슬러그}.md` 같은 임시 경로. **커밋하지 마라**) 그 파일을 넘기고, **생성 명령엔 `</dev/null`을 붙인다**(안 붙이면 Windows에서 glab이 stdin을 물고 무기한 행에 걸린다):
   `glab issue create --title "..." -d "$(cat {본문파일})" --assignee {아이디} --label "모듈:{이름}" </dev/null`
   — **고위험이면 `--label "고위험"` 추가**(1번에서 판정), 모호하면 `--label "대기(불명확)"`.
   — ★**루프·배치에서 특히 빠뜨린다**(분해 등록이 정확히 이 경우다): for 루프 안의 glab 호출에도 `</dev/null`을 **하나씩 다 붙여라**. 파일럿 2026-08-04 실측 — 루프에서 빠뜨린 `glab mr create` 2건이 **출력 한 줄 없이 무음 실패**했다(브랜치는 올라갔는데 MR만 없음. 루프는 에러도 안 보여주니 조회 전엔 성공으로 착각한다). 타임아웃 60~90초도 함께 걸어라.
   담당자는 해당 모듈 소유자(CLAUDE.md 모듈 표 기준. 내 모듈이면 나). **표에 소유자가 비어 있으면 임의 배정하지 말고 공통 개발자 지정 요청**. 분해면 4번의 위상순대로 선행부터.
5-1. ★**등록 직후 재조회로 확인한다** — `glab issue view {번호}` 로 **제목·수용 기준 체크박스·라벨·담당**이 의도대로 올라갔는지 눈으로 본다(`rules/gitlab-cli.md` 정본: 바깥에 남긴 산출물의 무음 실패·본문 깨짐은 조회로만 잡힌다).
   - 분해 등록이면 **발행한 번호 전부**를 `glab issue list`로 한 번에 대조해 빠진 장이 없는지 센다.
   - 깨졌으면 그 자리에서 고치고(본문 파일 수정 → `glab issue update`) 보고에 적어라.
6. 보고: 카드 번호 + `지금 착수하려면 /dev {번호} 또는 /fix {번호}` (등록만 하고 나중에 해도 된다 — 보드가 기억한다).
   분해 등록이면: 번호·제목·담당자 표로 보고 + 담당자별 @멘션 공지 한 줄 (각자의 /todo에 뜨게)

## ❌ 금지 — 그 순간 드는 핑계와 반박까지

| 하고 싶어지는 말 (핑계) | 반박 |
| --- | --- |
| "사소한 수정이니 카드 없이 바로 고치자" | 카드 없는 변경은 이력·검수·이유가 전부 증발한다 — 등록이 1분, 추적 복원은 불가능 |
| "수용 기준은 개발하면서 정하자" | /dev 의 게이트 단축과 검수가 이 필드에 의존한다 — 기준 없는 카드는 검수 불가 카드다 |
| "채팅으로 합의했으니 그걸로 충분" | 합의는 빨리, 기록(카드)은 반드시 — 채팅은 다음 세션의 AI도, 다음 주의 팀원도 못 읽는다 |
