# /done 단계 상세 — 본문이 가리킬 때 그 절만 읽어라

> `SKILL.md` 본문은 «무엇을 하는 단계인가 + 반드시 지킬 것»만 담는다. 이 파일은 그 단계의 **실행 순서와 실측 경위**다.
> **왜 뺐나**: 컴팩션은 스킬마다 **«앞 5,000토큰만 남기고 뒤를 자른다»**(공식). 7~10단계와 «금지» 절은 그 밖이라
> 대화가 길어지면 **통째로 안 읽혔다.** 보조 파일은 그 예산에 안 든다(읽을 때만 로드) — **잘려서 안 읽히느니 포인터로 읽히는 편이 낫다.**
> ※ **실측된 예외·우회**는 이 파일이 아니라 `함정.md` 다. 여기는 «정상 경로의 상세»다.

## §0 1·5단계 경위 — 왜 합치기가 리뷰 뒤인가, 왜 다시 조회하고, 왜 리셋하면 안 되나

**왜 합치기·시험을 리뷰 뒤(5·6단계)로 옮겼나 (2026-10-13 배포처 bnsone #610)**: 예전엔 «main 합치기 → 내 컴퓨터 시험 → 리뷰 → 서버 시험 → 머지» 순이라 main 이 움직일 수 있는 시간이 길었다. 실측(bnsone): 로컬 `npm test` 약 2분 · 서버 MR 파이프라인 6~11분 · 독립 리뷰는 한 카드 14~52분 — 시간이 큰 쪽은 시험이 아니라 서버와 리뷰다. 그 사이 남이 먼저 머지하면 다시 합치고 다시 시험해야 했다. **«합친 뒤 시험» 자체는 없애지 않는다**(무료 GitLab 은 병합 결과 파이프라인·머지 트레인이 없어 이게 1차 방어다). 병합 전 시험은 `/dev` 6단계가 이미 돌렸으므로 따로 두지 않는다.
- **병합이 리뷰 뒤로 가면서 생기는 일**: 병합이 «내 코드를 바꾸면»(마이그레이션 재생성·ADR 번호 이동·충돌 해결·병합 뒤 타입 오류 수정) 리뷰받은 판이 아니다 → 5단계 `after-merge` 판정이 `재리뷰` 를 내고 2단계로 돌아간다. main 쪽 파일만 바뀌었으면 `리뷰유효`. 판정은 **«합친 main 지점 대비 HEAD 에서 달라진 파일이 전부 리뷰받은 내 변경인가»** 로 한다 — main 이 건드린 파일이어도 병합 커밋에서 손으로 고쳤거나 병합 뒤 직선 커밋으로 고쳤으면 `재리뷰`.
  - **리뷰받은 내 파일을 main 이 «같은 파일의 먼 곳만» 고친 경우**(#677)는 `리뷰유효` — 합친 결과가 git 의 기계적 병합과 권한까지 같고, main 이 고친 줄이 내 줄과 4줄 이상 떨어졌을 때만. 가깝거나 손댄 흔적이 있으면 `재리뷰`. 줄만 보니 뜻이 이어진 경우(이름 바꿈 + 옛 이름 호출)는 못 잡는다.
  - 반대로 main 이 고친 내 파일을 «내 쪽만 채택»해 main 의 변경이 사라진 병합(`-s ours`·`--ours` 해결·main 이 지운 파일 되살리기)도 `재리뷰` 다 — HEAD 가 리뷰한 커밋과 같아 보여도 기계적 병합과 다르면 잡는다.
- **`$REV` = 마지막으로 리뷰어에게 넘긴 head SHA.** 2단계에서 리뷰 반영 수정을 커밋했으면 그 수정 뒤의 SHA 로, `재리뷰` 로 돌아가 증분 재리뷰를 마쳤으면 그 재리뷰의 head 로 **갱신**하고 5단계를 다시 한다. 4단계에서 digest·docs 수정 커밋이 끼면 리뷰받지 않은 내 변경이라 `재리뷰` 가 나온다 — 문서만이면 증분 재리뷰가 작다.
- **한계(솔직히)**: 파일이 안 겹쳐도 깨질 수 있다(한쪽이 함수 이름을 바꾸고 다른 쪽이 옛 이름 호출을 추가). 판정기는 흔한 길목(같은 파일·마이그레이션 순서·package·lock·shared·내가 쓰는 모듈 index 의 export 삭제·변경·CI·ADR 번호·글자 충돌)을 막을 뿐이다(배포처 #716 — 같은 모듈 다른 파일·남의 새 마이그레이션·안 쓰는 모듈 index 는 사유에서 뺐다. 그래서 «main 이 컬럼 이름을 바꾸고 내 코드·시험이 옛 컬럼을 쓰는» 갈래도 이제 머지 뒤 main 파이프라인이 잡는다). 나머지는 머지 뒤 main 파이프라인이 깨지면 즉시 revert 하는 2차 방어에 맡긴다.

**1단계 «세션 시작 이후 남이 한 일»을 다시 보는 이유**: 2026-08-31 실측 — 두 사람이 같은 시간대에 나란히 일했는데, 시작 스냅숏만 본 세션은 상대가 그 뒤 올린 MR·카드·머지를 **끝까지 못 봤다**(오너가 물어야 드러났다). **조회 한 번이 이 구멍을 닫는다.**

★**5단계 병합 뒤 «ADR 번호가 겹쳤나»를 한 번 봐라**: `ls docs/adr | cut -d- -f1 | sort | uniq -d` 가 비지 않으면 **멈춘다**. 채번은 «파일이 있는 것»만 보므로, 내가 push 안 한 브랜치에서 잡아 둔 번호를 남이 먼저 머지할 수 있다(2026-09-23 배포처 #311: 0076 이 겹쳐 파일명 + 그 번호를 인용한 **15곳**을 함께 옮겼다). **여기서 잡으면 옮기는 값이 싸고, 머지 뒤에 알면 비싸다** — 머지된 마이그레이션은 불변이라 그 안의 인용은 못 고친다(그래서 `rules/migrations.md`: 불변 파일엔 ADR 번호를 적지 않는다).

**5단계가 «병합»인 이유**: 작업 브랜치에는 내 커밋이 있어 앞으로 감기(`pull --ff-only`)가 안 된다 — `git fetch origin` 후 `git merge origin/main` 이 맞다. **본 클론 main «따라잡기»(`pull --ff-only`, CLAUDE.md 세션 규칙)와 다른 일이다** — 섞으면 main 에 병합 커밋이 생기거나, 작업 브랜치에서 ff-only 가 멈춘다(2026-09-10).

**5단계 마이그레이션 순서·적용 (마이그레이션 도구 있는 스택만)**: 병합으로 받은 새 마이그레이션을 로컬 DB 에 적용한다 — 명령은 CLAUDE.md '실행·테스트'. 병합에서 main 에 내 것보다 나중 타임스탬프의 새 마이그레이션이 들어왔으면 **내 마이그레이션을 최신 뒤로 재생성**한다(전역 직렬 자산 — 순서가 꼬이면 스키마가 깨진다). 적용됨·미확인인 내 파일은 원본을 보존하고 순서 해결 전 DB 적용·머지를 멈춘다. 재생성은 내 코드가 바뀌는 일이라 `after-merge` 가 `재리뷰` 를 낸다.

**5단계 `P3009` 상세**: ★**`P3009` 가 나오면 리셋이 아니라 `migrate resolve --applied <이름>` 이다** — 컨테이너 기동이 마이그레이션을 자동 실행하는 스택에서 호스트에서도 동시에 돌리면 한쪽이 `42P07 … already exists` 로 죽고 **실패 기록만 남아 그 뒤가 전부 막힌다.** DB 는 멀쩡하고 **기록만 어긋난** 상태라 `migrate deploy` 를 다시 돌려도 안 풀린다. ⚠️**먼저 CLAUDE.md '실행·테스트' 를 보고 컨테이너가 이미 돌리는지 확인하라 — 그러면 5단계의 적용을 건너뛴다**(2026-09-07 bnsone 실측: 2건이 며칠째 안 들어간 채였고 남의 모듈 테스트가 빨개져서야 드러났다).

## §1 리뷰 반영 수정은 커밋한 뒤에 재검증한다 (2단계)

★**리뷰 반영 수정은 «커밋한 뒤에» 재검증·돌연변이를 돌려라** — 이 단계는 본질적으로 «미커밋 수정이 쌓인 상태»라 복원 명령이 그 수정을 통째로 지운다(2026-08-25·08-26·09-03 실측 **3회**). 복원 확인도 `git diff --quiet`(커밋 상태와 같아지면 «OK»로 보인다)가 아니라 **「내 수정이 아직 있나」를 grep 으로** 하라. 스크립트로 짤 땐 **/dev 6단계가 가리키는 dev `함정.md` §6 의 첫 줄 게이트**를 박아라(6단계 본문엔 그 한 줄이 없다).

## §2 수용 기준 대조 — 「검수 방법」이 실물로 성립하는지까지 (4단계)

★**수용 기준만 보지 말고 카드의 「검수 방법」 문구에 적힌 화면·계정·양식이 실물로 존재하고 그 조합이 성립하는지 확인하라 — 라우트(`nav`)와 시드를 직접 열어라.** 2026-09-03 실측: 「근태 화면에서 확인」이라 안내했는데 **그 화면이 없었고**(`nav: []`), 안내한 계정 조합도 시드상 성립하지 않아(결재선 1단계라 상신 즉시 전결) 검수자가 절차를 따르다 두 번 막혔다.

- ★**검수 표의 행마다 «그 상태가 검수 서버에 지금 있는가»도 조회하라** — 로컬 DB 에서 내가 만든 데이터로 보고 「있다」고 착각하지 마라(2026-10-08 bnsone #495: 사용 불가 자원 표본이 시드에 없고, 삭제용 표본은 예약이 붙어 삭제 불가였다 — 사람이 두 화면에서 막혔다). 없으면 사람에게 넘기기 전에 **내가 서버에 임시 데이터를 만들어 확인하고 원래대로 되돌린다**(되돌릴 수 없는 데이터면 만들지 말고 카드에 «셋업 요청»). **데이터 세팅은 AI 몫, 사람에겐 눈 확인만 부탁한다.**
- ★**「MR !번호」처럼 «아직 없는 값»이 필요한 갱신은 7단계(MR 생성) 뒤에 한다** — 이 단계에서 관례대로 번호를 적으려다 **짐작으로 채우게 된다**(2026-09-04 bnsone 실측: 맞았지만 위험한 패턴). 체크박스·진행 표기는 지금 하고, 번호가 들어가는 줄만 뒤로 미뤄라.
- ★**대조 결과를 카드 본문 체크박스에 반영한다**(`- [ ]` → `- [x]`, `glab issue update $0 -d`로 본문 갱신) — 증거 댓글만으론 목록에 `0/N`으로 남아 완료 판별 불가(bnsone #6·#16·#17·#18 — `함정.md` §8). 못 채운 항목은 `[ ]`로 두고 사유를 댓글에. ※갱신 방법의 함정은 **`함정.md` §3** — 갱신 전에 읽는다.

- ★**화면 카드는 수용 기준 문구만 대조하지 마라 — 닫기 전 «이번에 뺀 것»·«디자인과 다른 곳»이 카드 번호나 `_digest.md` 줄로 이어졌는지 본다**(아래 ㉮㉯ 와 같은 대조). 안 이어졌으면 «디자인대로»라고 쓰지 마라 — bnsone 10-12, 〔검수확인〕으로 닫힌 화면 13장의 본문 폭이 처음부터 달랐다. 증거: `scripts/design-metrics.cjs` 가 있으면 `/inspect` 가 돌린 `--compare` 결과(어긋남 0 또는 목록).

### §2 ㉮ 미룬 일 → 카드 번호 대조
(※ 이 파일 §3 이 말하는 «§2-a·§2-b»는 `함정.md` 의 절이다 — 여기 ㉮㉯ 와 다르다.)
★**이 카드가 «미룬 것»을 하나씩 세고, 각각에 카드 번호가 있나 본다.** 2026-09-17 bnsone 1차 요구 전수 대조: «후속 카드로»·«별도 카드»·«범위 밖(후속)»·«STEP N 에서 정한다»만 적고 **안 생긴 일이 19건**(예고 카드 11 · 분해안 미발행 5 · 1차 기능 3)이었다. 문장은 할 일을 «치운» 효과만 있고 카드가 생겼는지는 아무도 안 봤다.
- 어디서 세나: **카드 본문·댓글**(`glab api "projects/:id/issues/$0/notes?per_page=100"` 을 `jq -r '.[].body'` 로) · **이 브랜치 diff 의 문서**(`bash scripts/check-deferred.sh` — CI `mr-checks` 의 `deferred-check` 와 같은 검사) · 이제 쓸 **완료 댓글·MR 본문**. 찾는 말 = `후속`·`별도 카드`·`범위 밖`·`나중에`·`STEP N 에서`·`착수 직전 ADR`·`남의 모듈`·`소유자 몫`·`{모듈} 소관`.
- 번호가 없으면 **7단계 묶음 승인에 «카드 N장 발행»을 한 줄로 얹고** 승인되면 `/card` 로 만든 뒤 그 번호를 원문 자리에 적는다. 카드가 필요 없으면 그 자리에 `(카드 불요: 사유)`.
- ⚠️**«범위 밖»을 수용 기준에서 뺀 1차 요구**면 카드만으론 부족하다 — 그 STEP `_digest.md` «미해결» 절에도 한 줄(다음 세션이 요구 쪽에서 찾을 수 있게).

### §2 ㉯ «스펙과 달라진 점»은 기억이 아니라 대조로 판정한다
★**완료 댓글에 «달라진 점 없음»을 쓰기 전에 카드 댓글에서 결정 흔적을 찾아 digest 와 맞춰라.** 2026-09-17 bnsone 실측: 오너 확답으로 설계와 다르게 만든 카드(#191)가 완료 댓글에 «달라진 점 없음»이라 적었고, 스펙 이탈 결정 여러 건(익명 게시판 조합·결재선 변경 차단 등)이 **카드 댓글에만** 남았다 — 기획자는 카드를 안 본다.
- 찾는 말(카드 본문·댓글): `오너 확답`·`오너 결정`·`확답`·`정본에 없어`·`스펙과 다르`·`설계와 다르`·`기획 확인`.
- 걸린 것마다 `grep -rn "#$0" docs --include=_digest.md` 로 **digest 에 그 카드 번호가 있나** 본다. 없으면 그 STEP `_digest.md` «미해결·질문» 절에 「스펙과 달라진 점·이유·결정자·카드」를 적고(이 MR 에 포함) **그 줄이 기획 질문 묶음에 실린다**(`scripts/collect-planner-questions.sh` — `rules/docs.md`).
- 걸린 것이 있는데 digest 에 안 적었으면 **«달라진 점 없음»이라고 쓰지 마라** — 그건 대조를 안 했다는 뜻이다.

## §3 7단계 상세 — 묶음 승인·MR 생성·머지

**⏸ 묶음 승인 — 여기서 딱 한 번 선다.**

- ★**한 화면 5줄 이내로** 「①(공통 영역이면) 팀 채팅 공지했나 ②올라갈 내용이 무엇인가 ③이대로 머지 예정」을 보여주고 **OK 하나**를 받는다. ①②③은 번호 없는 불릿(•)으로 적고 번호는 «OK/수정» 선택지에만 쓴다. 표·파일 목록 금지(근거는 카드에 — CLAUDE.md '남기기 전 미리보기').
  사람에게 이 셋은 **"이대로 main에 넣을까?" 한 질문**이다. 따로 물으면 정보량 0인 정지가 늘고, 잦은 정지는 요약을 길게 만들어 **아무도 안 읽는 도장찍기**가 된다(2026-08-28 실측: 한 카드 8회 정지 중 결과를 바꾼 답은 2회. 오너 결정 "1").
- **이 묶음은 셀프승인 레인 한정.** 동료 승인 레인이거나 파이프라인이 빨간불이면 **지금까지대로 다시 선다.** 머지 후 파이프라인 결과는 사후 보고.
- ★**남은 미커밋이 있으면 경로 지목 add — `git add -A`·`add .` 금지**(bnsone 15c882c — 상세 /dev 7단계).
- **이번 diff가 새 필수 환경변수를 도입했으면** 로컬 기동 3경로(`docker-compose*`·`.env.example`·엔트리포인트)를 **같은 MR에서** 채웠는지 확인(하나만 빠져도 남의 로컬 기동이 통째로 죽는다 — bnsone #63 실측).
- **승인 화면에 «셀프 머지»라고 쓰기 전에 이번 diff 의 경로를 CI 고위험 경로 규칙(`.gitlab-ci.yml` 의 `high-risk-paths`·`high-risk-hard`)과 대조하라**(`git diff --name-only origin/main...HEAD`). 위 «공통 영역» 목록에 없어도 `scripts/test-*` 같은 이름 규약에 걸리면 게이트가 manual 로 서서, 승인 뒤에 정정·재승인 한 바퀴가 든다(bnsone #727 실측).

**MR 생성 — `glab mr create --remove-source-branch` (설명에 "관련: #$0").**

- ★**브랜치 삭제는 세 경로 «전부» 명령에 박아라 — 프로젝트 설정에 맡기지 마라**: 생성 `--remove-source-branch` · 일반 머지 `glab mr merge -d` · raw API 우회 `-f should_remove_source_branch=true`. 한 곳만 넣으면 auto-merge 실패 → 우회로 빠지는 갈래에서 샌다. **머지를 확인한 뒤 로컬도** `git branch -d {브랜치}` → `git fetch --prune`(§4 — 호출을 나눠서). GitLab 설정이 켜져 있어도 glab 경유 MR 은 `force_remove_source_branch=false` 로 남는다(2026-09-07 bnsone 실측: 서버 브랜치 68개 중 **65개가 머지 후 껍데기**, 로컬 86개 중 58개가 `[gone]` 유령 — 작성자 세 사람 전원이라 습관이 아니라 절차 누락이었다).
- ★**MR 본문에 `Closes #N`(`Fixes`·`Resolves` 포함) 금지 — `관련: #$0` 링크만**: 머지 순간 카드가 자동으로 닫힌다(`함정.md` §8). **예외 없다** — 셀프완료·`/ui`도 §4 절차로만 명시적으로 닫는다.
- **MR 본문도 여러 줄이다** — 작성·재조회 규칙 정본 = `rules/gitlab-cli.md`(상시 로드). 루프 다중 MR에서 특히 무음 실패한다 — 생성 후 `glab mr list` 재조회.

**머지.**

- ★**auto-merge는 파이프라인이 running/pending일 때만 건다.** 이미 종결(success)이면 걸지 말고 **즉시 일반 머지**(`glab mr merge -d` — `-d` 를 빼면 브랜치가 남는다) — 끝난 파이프라인 위에 걸면 발동할 이벤트가 없어 **영구 대기**한다(파일럿 #14 실측).
- **status `manual`(blocked)은 실패도 진행도 아니다 — 게이트 승인 대기**: auto-merge 말고 아래 고위험 절차부터. 판정은 `node scripts/pipeline-verdict.cjs <PID>` 1행 토큰으로(status 한 값 판정 금지).
- **1행 `취소` 는 실패도 통과도 아니다**(더 새 커밋에 밀려 끊긴 것 — 배포처 bnsone #826. 이 판정이 정본, 다른 절은 여기를 가리킨다): ①MR 대기 중이면 그 MR 의 현재 `head_pipeline` 을 다시 판정한다(같은 ID 면 대신 도는 것이 없다 — 사람 취소·시간 초과일 수 있으니 사람에게 보고) ②머지 뒤 main 이면 검수 서버가 알려 주는 배포 커밋(health 응답의 sha 등)이 내 머지 커밋의 후손인지로 배포를 판정한다(그런 값이 없으면 사람에게 보고) ③어느 쪽이든 revert·재작업 사유로 읽지 않고, `종결초록` 처럼 «끝났다·머지 가능·배포됨»으로도 세지 않는다.
- ★**auto-merge 설정이 실패하거나("requires a passing pipeline"·"Not Allowed") 안 걸리면 `함정.md` §1을 읽고 처리하라** — 실측된 우회가 있다. 포기 전에 반드시.
- ★**고위험 카드면**(`고위험` 라벨 또는 CLAUDE.md '머지 등급'의 고위험 유형) **판정한 즉시 `함정.md` §2를 읽고 그대로 실행하라**(§2-a 동료=선택/§2-b 셀프=표준/§2-c 잡 없음 — 레인·티어·상황마다 실행법이 다르다. 늦게 읽으면 승인 단계에서 되돌아온다). **게이트 잡이 실제 생성됐는지 잡 목록으로 확인하기 전엔 auto-merge·셀프 머지 금지**(라벨 선행·확인 명령 = §2).

**머지 전 경고 확인 (2026-10-22 배포처 bnsone #789)** — `allow_failure` 잡(`mr-warnings`·`density-check`)의 경고는 파이프라인을 초록으로 두므로 «읽었다»는 증거가 없었다. **일반 머지·auto-merge 등록 직전에** `node scripts/warning-ack.cjs <MR iid>` 1행을 읽는다(사용자에게 경고를 대신 읽히지 마라 — 네가 읽고 경고별로 처리한다).
- `경고없음`·`경고처리됨` → 진행. 경고 없는 MR 은 댓글·승인을 요구하지 않는다.
- `경고미처리` → 잡 로그를 **네가 읽고**, 2행 이하가 알려 주는 머리 줄(`sha=… pipeline=… job=…`)과 항목 줄을 MR 댓글로 남긴다: `- <키>: 수정함|수정불필요 — <근거>`. 고쳤으면 새 커밋→새 파이프라인이라 기록은 **새 sha·잡 번호로 다시** 쓴다(옛 기록은 재사용되지 않는다). 경고 내용이 같고 커밋만 바뀌었으면 로그를 다시 읽은 뒤 새 번호로 고쳐 쓴다.
- `미종료` → 경고 잡이 안 끝났거나 파이프라인이 낡았다. **끝나기 전에 auto-merge 를 걸지 마라**(경고를 못 본 채 병합된다). 파이프라인이 이미 success 면 기존대로 일반 머지.
- 조회 실패(종료 2)는 `경고없음` 이 아니다 — 같은 조회를 한 줄로 직접 돌려 원인을 확인한다.
- **한계(솔직히)**: 도구는 «대상(sha·pipeline·job) 일치 + 모든 항목 존재 + 처리값 + 근거 비어 있지 않음» 만 본다 — 근거의 진위는 못 가린다(리뷰의 몫). 경고 잡을 `allow_failure: false` 로 바꿔 대신하지 마라. 항목 키는 로그에서 «[검사이름] 시작» ~ «[검사이름] ⛔ 실패» 사이(`ci-run-checks.sh` 의 실제 순서 — 결과 머리 줄이 출력 «뒤»에 온다)의 줄머리 `[경고:키]`(없으면 검사이름, 실패 구간이 없으면 잡 이름, ✅ 통과 구간의 키는 버림) — 경고 출력부가 이 접두를 찍어야 항목이 세밀해진다. 자기시험 = `scripts/test-warning-ack.sh`.

**머지 직전에 main 이 또 움직였을 때 (2026-10-13 배포처 bnsone #610)** — 파이프라인이 끝나 머지(일반 머지·auto-merge 걸기)를 바로 앞둔 때 `git fetch origin` 후 `node scripts/done-merge-verdict.cjs main-moved`. 1행만 읽는다.
- `최신`·`그대로` → **합치지 않고 머지한다.** `그대로` = main 이 새로 바꾼 파일이 내 변경과 안 겹치고 위험 경로·글자 충돌이 없다는 뜻이다. 합친 결과의 시험은 머지 뒤 main 파이프라인이 하며, 빨개지면 즉시 revert 한다(`_reference/revert.md`).
- `합치기`·판정 불능(종료 2) → SKILL 5·6단계(합치기·시험)를 다시 하고 올린다 — 서버 시험이 한 번 더 돈다고 사용자에게 알린다. 다시 합친 결과 `after-merge` 가 `재리뷰` 면 2단계로.
- `합치기` 가 되는 것: 같은 파일 · main 의 새 마이그레이션(**내 변경에도 스키마·마이그레이션이 있을 때만** — 순서·스키마 충돌) · `package.json`·lock · `src/shared`(**시험 파일 `*.test.*`·`__tests__/` 제외**) · 모듈 `index.ts`(**기존 export 줄이 지워지거나 바뀌었고, 내 코드가 그 모듈을 쓸 때만** — 내 모듈이면 쓴다고 본다. export 를 더하기만 한 변경은 사유가 아니다) · `.gitlab-ci.yml` · ADR 번호 겹침 · 글자 충돌.
  - **같은 모듈 폴더(`src/modules/{x}`)라는 이유만으로는 `합치기` 가 아니다**(2026-10-19 배포처 #716 — 남의 무관한 변경 때문에 `합치기` 가 세 바퀴(바퀴당 약 40분) 돌았다). 같은 파일이면 «같은 파일», 줄이 부딪히면 «글자 충돌» 이 잡는다. **한계(솔직히):** 파일이 안 겹쳐도 깨질 수 있다(함수 이름을 바꾸고 다른 파일에서 옛 이름 호출이 늘어남) — 머지 뒤 main 파이프라인 + revert 가 2차 방어다. `그대로` 인데 머지 뒤 main 이 빨개지면 기준을 다시 조정할 근거이니 카드로 남겨라. «쓴다»의 판별은 본문에 `modules/<이름>` 이 나오는지다 — import 방식이 다른 repo 면 판정기의 정규식을 고쳐라.
  - **판정기가 `합치기` 를 내면 사용자 선택으로 건너뛰지 마라** — 기준이 좁혀진 뒤에도 나온 `합치기` 는 진짜 겹침이다. 건너뛴 이력은 규칙 이탈로 카드에 남긴다.
  - **단 main 의 위험 경로(마이그레이션·package·lock·shared·모듈 index·CI)는 «내 변경에 코드가 있을 때만» 사유다** — 문서만 바꾼 MR 이 남의 `package.json`·CI 변경 때문에 계속 `합치기` 가 되던 것이 실제 사례다. 문서만 바꿨으면 위험 경로는 «참고» 줄로만 나온다.
  - **fail-closed:** «문서로 확인된 것만» 비코드이고 나머지는 전부 코드다. 비코드 = 마크다운·텍스트(어디든) + `docs/` 아래의 그림·html 등(`docs/` 의 json·yaml·스크립트는 CI 검사가 읽으므로 코드). `scripts/*.sh·cjs·ts`·루트 설정·`.claude/hooks`·`.env.example`·`k8s/`·`public/` 등은 전부 코드다(독립 리뷰가 목록 방식의 fail-open 을 재현했다). **같은 파일·ADR 번호·글자 충돌은 문서만 바꿔도 그대로 사유다.**
  - ⚠️**판정기는 «작업 폴더(워크트리) 안에서» 돌려라** — 본 클론(main)에서 돌리면 리뷰한 커밋이 조상이 아니라서 `재리뷰` 로 오판한다(2026-10-13 배포처 #626: 같은 리뷰 SHA 로 두 결과가 갈렸다). 판정기는 현재 폴더의 HEAD 를 본다.
  - 자기시험 = `scripts/test-done-merge-verdict.sh`. 경로 가정(`src/modules`·`src/shared`·`docs/adr`·마이그레이션 폴더 이름)이 다른 repo 면 판정기 정규식을 그 repo 에 맞게 고친다. **한계(파일이 안 겹쳐도 깨질 수 있다)는 §0.**
  - 이 판정은 **머지를 거는 순간**의 것이다 — auto-merge 를 걸어 두면 파이프라인이 도는 동안 main 이 또 움직여도 재판정 없이 병합될 수 있다. 이 틈도 머지 뒤 main 파이프라인 + revert 가 2차 방어이고, 걱정되면 파이프라인이 끝난 뒤 판정하고 일반 머지(`-d`)한다.
- **합친 뒤(5·6단계)에 시험 말고 셋을 더 본다**(2026-10-13 배포처 #599 — 초록 판정 뒤 main 에 두 건이 먼저 들어와 import 충돌이 났고, 새로 들어온 칸이 내가 없애던 옛 모양이었다): ①내가 없애거나 바꾼 패턴(이름·옛 모양)이 main 의 새 코드에 들어왔는지 grep ②화면이면 한 번 더 띄워 눈으로 ③새 SHA 의 파이프라인을 기다린다.

## §4 8단계 상세 — 머지 확인·로컬 정리·배포 화면

**머지 완료 확인 = `glab mr view <MR iid>` 로 `state`=`merged`를 눈으로 본다**(추정 금지 — auto-merge 설정·파이프라인 초록은 확인이 아니다). `merged`가 아니면 화면 확인·§5로 가지 말고 상태를 그대로 보고 후 `함정.md` §4·§1 경로로.

- ★**`merged` 를 본 그 자리에서 로컬도 정리한다**: `git checkout main` → `git pull --ff-only origin main` → `git branch -d {작업브랜치}` → `git fetch --prune`(한 호출에 하나씩 — `&&` 로 이으면 `bundle-guard` 가 되돌려 보낸다). 안 지우면 upstream 이 사라진 «유령» 브랜치가 쌓인다(2026-09-07 bnsone 실측: 로컬 86개 중 84개가 이미 main 에 포함, 그중 **58개가 `[gone]`**).
- ★**이슈 워크트리에서 일했으면(`git rev-parse --git-dir` ≠ `--git-common-dir`) `merged` 를 본 뒤 그 워크트리도 지운다** — 안 지우면 쌓이고, 세션이 바뀌면 «지워야 한다»는 기억도 사라진다(2026-10-07 bnsone 실측: 워크트리 7개). 위 `checkout main` 은 본 클론이 main 을 쥐고 있어 실패하니 하지 마라. **내가 만든 `issue-$0` 만** — 남의 워크트리는 건드리지 마라.
  - 지우기 전 **넷 다**: ①`merged` ②`git -C {경로} status --short` 비어 있음 ③푸시 안 된 커밋 0(`git -C {경로} log @{u}..` 가 비었거나 upstream 이 `[gone]`) ④다른 세션이 쓰는 폴더가 아님. 하나라도 어긋나면 지우지 말고 사유만 보고.
  - 순서(한 호출에 하나씩, 울타리 밖): 한 줄로 알린 뒤 `docker compose -p issue-$0 down`(`-v` 금지) → 아래 볼륨 줄 → 링크면 `rm {경로}/node_modules` 먼저 → `git -C {본클론} worktree remove {경로}`(`--force` 금지) → `git -C {본클론} fetch --prune` → `git -C {본클론} branch -d {브랜치}`. 레시피 = `_reference/worktree.md`.
  - **DB 볼륨 `issue-$0_pgdata`**(안 지우면 로컬에 쌓인다 — 2026-10-19 bnsone 실측 6개): `down` 직후 위 넷 다 + ⑤`docker ps -a --filter volume=issue-$0_pgdata` 가 비어 있고 ⑥이름이 방금 내린 프로젝트 `issue-$0` 의 것일 때만, 한 줄로 알린 뒤 `docker volume rm issue-$0_pgdata` **한 개만 이름으로**(`prune`·와일드카드·`down -v` 금지). 하나라도 어긋나면 지우지 말고 사유만 보고. 주인 불명의 옛 볼륨은 건드리지 마라.
  - **`-d` 가 «not fully merged» 로 거절되면**(본 클론의 로컬 main 이 뒤처졌을 때 난다 — 2026-10-07 bnsone) `git -C {본클론} merge-base --is-ancestor {브랜치} origin/main` 이 **EXIT=0 일 때만** `-D`. 아니면(스쿼시 머지 등) 지우지 말고 사유만 보고 — 단 `node scripts/worktree-sweep.cjs`(`git fetch origin` 뒤) 가 그 워크트리를 «정리 가능»(바꾼 파일이 전부 main 과 같은 내용 · 머지된 MR 의 sha 일치)으로 판정하면 `-D` 해도 된다. **같은 이름 브랜치에서 MR 을 닫고 다시 만든 경우**가 이 모양이다(닫힌 MR 의 커밋이 끝에 남아 «main 에 없음» 으로 보인다).
  - **`merged` 를 못 보고 세션을 끝냈으면(auto-merge 대기 등)** 이 정리는 안 돈다 — 다음 `/todo` 가 `worktree-sweep.cjs` 로 «정리 가능» 후보를 올린다(`todo/스캔상세.md` §6). 그때 위 넷 다를 다시 확인하고 지운다.
- ★**워크트리를 지웠으면 그 뒤의 조회는 «절대 경로»로 하라** — 셸의 작업 폴더가 사라진 채 남아 **상대 경로 `grep` 이 조용히 «0건»을 낸다**(`| wc -l` 이 `No such file` 을 덮는다). 「다 끝났다」로 읽히는 자리다 — **0 이 나오면 결론 전에 경로부터 의심하고 «알고 있는 절대 경로»로 다시 재라**(⚠️그 자리의 `git rev-parse --show-toplevel` 은 cwd 가 없어 exit 128 로 죽는다 — 쓰려면 `git -C {경로}` 로. 2026-09-16 bnsone 실측: 실제 5·16 을 0·0 으로 봤다).
- ★**이번 diff에 설정·매니페스트 파일이 있으면**(`k8s/*.yaml`·configmap·env 류) **지금 `함정.md` §7을 읽어라** — "머지=반영"이 성립하지 않는 유형이다.
- 머지가 확인되면 **배포 화면 먼저 확인**: **AI 가 먼저 `/inspect $0` 절차로** 배포(또는 로컬) 화면의 렌더·클릭 왕복·이상 입력을 확인하고 증거를 남긴다 — 사람 확인은 보조(검수 표의 «사람이 볼 것» 칸). **확인 방법을 사람에게 선택지로 묻지 마라**(AI 몫 단계다 — 「확인 없이 검수요청」 선택지 금지). UI 파일이 없어도 화면 값이 바뀌는 카드(판정·계산)는 화면 카드다 — 특정 데이터가 필요하면 `inspect/함정.md` §3 · **화면 확인 전 검수요청 전환 금지**
- ★**파이프라인이 `success`여도 경고를 확인해 보고하라**(실패한 잡 이름 + 로그 요약 한 줄) — `allow_failure` 잡은 실패해도 `success`로 보인다. **조회법·근거는 `함정.md` §6.**
- auto-merge 대기 중인데 세션을 끝내야 하면(또는 파이프라인이 failed면): **끝내기 전에 `함정.md` §4를 읽어라** — 그대로 끝내면 안 되는 조건이 있다.
- **화면 없는 카드**(인프라·docs·API 노출)는 이 단계·검수요청 없이 상태 전이표의 **셀프 완료** 경로다 — **`함정.md` §9를 읽고 그대로 실행하라**(체크박스·라벨 순서를 틀리면 조용히 샌다).

## §5 9단계 상세 — 라벨 전환·멘션

**`진행중` 제거 + `검수요청` 추가(둘 다 명시적으로**, 예: `--unlabel 진행중 --label 검수요청`**)** + 댓글 — 라벨 add/remove는 별개다. `진행중` 잔존 시 /metrics 리드타임에서 경고 없이 빠진다(파일럿 #14).

- ★**라벨 먼저 → 댓글 나중** — 알림은 **댓글 시점의 라벨**로 걸러지고 라벨 부착은 알림 사건이 아니다(bnsone 2026-08-13 — `함정.md` §8). 늦게 달았으면 재알림 댓글 하나 더.
- ★**부탁 댓글만 그렇다 — 완료·기록 댓글은 반대로 라벨을 뗀 뒤에 단다**(안 그러면 끝난 일이 초인종을 울린다. 검수 완료 = /todo `검수.md` §2, 승인 완료 = `함정.md` §2-a).
- **검수 부탁 댓글에 표가 있으면 칸을 «AI 가 직접 본 것 / 사람이 볼 것»으로 나눠라** — 섞으면 사람이 이미 확인된 것까지 다시 따라 하다 막힌다(§2 서버 데이터 조회 결과가 «AI 가 직접 본 것» 칸에 들어간다).
- **전환 후 `glab issue view $0`로 라벨이 실제 바뀌었는지 재조회한다**(명령 성공 출력≠반영 — 재조회가 확인이다)

  ({검수자} = 카드 "검수" 필드 → 비면 {카드담당자}(assignee) → 없으면 {카드작성자} — 모두 실행 시점에 `glab issue view $0`에서 읽는다. 전담 검수자는 없다)

## §7 완료 보고 증거

사람에게 하는 최종 보고는 **①한 줄 결론(무엇이 어떻게 달라졌나) ②사람이 할 일(없으면 «없음») ③알아둘 위험** 순서의 쉬운 말로 쓴다. 전문용어는 처음 쓸 때 한 줄 풀이를 붙인다(배포처 bnsone 751 — 또 반복된 지적).
**직접 확인한 증거**(`npm test` 결과 요약 · MR !번호 · 파이프라인 상태 · 해시 · 검수 서버 sha)는 카드 댓글에 적고, 채팅에는 확인한 사실을 사람 말로 한 줄만 둔다 — 증거 요구는 그대로고 둘 곳만 다르다.
확인 못 한 단계가 있으면 "완료" 대신 **어디까지 확인했는지**를 보고하라.

### 검수 안내표 — 사람 확인이 필요한 보고(/dev 7단계·/done 완료)는 끝에 채팅으로 직접 넣는다
«검수 서버에서 확인해 주세요» 한 줄과 «카드 댓글 참고»로 대신하지 마라 — 사용자가 웹에 들어가 댓글을 찾아야 하는 길이 반복 지적됐다(배포처 bnsone #242·#441·#557·#532). 카드 댓글과 채팅은 **같은 표 하나**다.
- 열: `번호 | 열 주소(클릭되는 링크)·계정 | 하실 일 | 통과 모습 | 볼 수 있는 때`. 번호는 이 표의 행 번호에만 쓴다. «하실 일»·«통과 모습» 칸은 화면에 보이는 글자·버튼 이름으로 쓴다 — 코드·ID·해시 금지.
- **«볼 수 있는 때»**: 오늘 못 보는 칸(예: 휴일이어야 보이는 버튼)은 «언제 가능한지»와, 그때까지의 **대체 확인**(AI 가 로컬에서 본 증거)을 나눠 적는다. 대체 확인을 사람 확인으로 둔갑시키지 마라.
- 화면 문구·위치는 **코드에서 확인한 것만** 쓰고, 못 본 것은 «확인 못 함»이라 적는다.

**마지막 `▶ 다음` 서식 — 카드 상태로 정한다(AI 의 «이어갈 맥락이 있나» 판단에 맡기지 마라, 긴 보고에서 빠진다).**
- 보고를 쓰기 전에 카드를 재조회해(`glab issue view $0`) **카드가 «열린 채»인지** 본다: 라벨이 `진행중` 으로 남았거나 · 체크박스가 미완이거나 · 남은 조각이 있다.
- 열린 채이고 **이 세션이 그 카드에서 작업했으면**(커밋·MR·카드 변경이 1건이라도) → 마지막 줄 = `▶ 다음: /handoff (남은 일 {쉬운 말 한 줄}) → 새 세션에서 /dev $0`. **`/handoff` 가 첫 선택지**다 — `/dev $0`·`/todo` 만 쓰고 끝내지 마라(2026-10-07 bnsone #468 실측: 조각 하나를 머지·확답까지 끝내고 카드가 5/10 으로 열려 있는데 `/handoff` 안내가 빠져, 사용자가 직접 쳐서야 인계됐다).
- **이 세션이 그 카드에서 커밋·MR·카드 변경을 한 게 없으면**(남이 머지한 뒤 `/done` 만 호출됐으면) 인계할 맥락이 없다 — 열린 채여도 해당 없음 → `/todo`(2026-10-07 bnsone #298: 새 세션에 «왜 또 handoff?» 지적).
- `검수요청` 으로 넘어가 남은 조각이 없으면 해당 없음 → `/todo`.

## §9 리뷰 방식과 수준 (2026-09-16 개정 — 기본 = 단일 독립 리뷰)

### 기본 = 단일 독립 리뷰 (2026-09-16 오너 결정)
- **근거(bnsone 실측)**: 최근 25개 카드의 리뷰 50회를 셌다. **크게 돌린 리뷰의 확정은 대부분 사소했다**(에이전트 40·25분 → 확정 10건 전부 사소 · 18·10분 → 4건 전부 사소). **작게 돌려도 «직접 실행해 재현하라»고 시킨 리뷰가 중요한 결함을 잡았다**(같은 날 단일 리뷰 3회 → 재현된 결함 6건). **반복 회차는 대부분 직전 수정분·스스로 덧붙인 것을 물었다.** ⚠️기록이 성겨(토큰 20%·결함 위치 14%만 적힘) **경향이지 증명이 아니다** — 그래서 아래 기록 칸을 고정했다. 한 달 뒤 같은 방식으로 다시 재서 유지·조정한다.
- **리뷰어 1명(새 문맥 에이전트)에게 반드시 줄 것**: ①**작업 폴더 절대경로** + 첫 행동으로 `git -C {경로} rev-parse HEAD` 를 지정 SHA 와 대조, 다르면 멈추게 ②판정마다 **직접 실행해 재현** — 재현 명령·기대/실제 종료코드를 붙이게(임시 저장소·스크래치패드 절대경로에서, 원 저장소에 파일을 만들지 말게 · 돌연변이용 수정은 `git archive` 사본·임시 워크트리에서 — 원 저장소 추적 파일을 고치거나 `checkout` 으로 되돌리지 말게: 작성자의 미커밋 수정이 지워진다) ③**범위를 좁게** — 이 diff 와 그 문장·코드가 가리키는 실물만 ④**가장 비싼 결함을 먼저** — 막으면 안 되는 것을 막는가(헛FAIL), 새는가(헛PASS) ⑤추측 금지 — 못 본 것은 «확인 못 함» ⑥출력 = confirmed(재현한 것만) / advisory / 머지 가능 예·아니오. 리뷰 렌즈에 **과잉설계**도 넣는다.
- **리뷰어에게 하나 더: 임시 워크트리에 `node_modules` 를 junction·symlink 로 잇지 말고, 정리에 `git worktree remove --force` 를 쓰지 마라** — 링크를 따라가 작성자 폴더의 `node_modules` 를 지운다(bnsone #753 실측 — `npm ci` 로 복구). 의존성이 필요하면 그 트리에서 설치하게 하라.
- **diff 가 규칙·스킬 문서(`CLAUDE.md`·`.claude/rules/**`·`SKILL.md`·보조 파일)를 줄이거나 고쳤으면 리뷰어에게 하나 더 준다** — «빠진 문장이 있나»만 물으면 «금지 → 설명»이나 한정어(`만`·`전에`·`먼저`·`내 클론이어도`) 탈락처럼 **약해진 문장**은 통과한다(2026-10-01 배포처 #423: 리뷰 2회 «빠진 규칙 0건», 문장 단위 대조로 11곳 약화). 지시: «옛 판에서 `금지`·`하지 마라`·`않는다`·`만`·`전에`·`먼저`·`사람이` 가 든 문장마다, 새 판(또는 항상 읽히는 다른 층)에서 **같은 강도**로 살아 있는 위치를 대라 — 없으면 결함». 낱말 건수 전후 비교는 단서일 뿐이다(중복을 걷어도 준다).
- **diff 가 `Dockerfile`·앱 이미지 구성(베이스 이미지·apt/apk 패키지·빌드 단계)을 바꿨으면 리뷰어에게 하나 더 준다**: «새 이미지를 실제로 빌드해 앱이 기동하는지(런타임 라이브러리·엔진 적재까지) 직접 실행해 대라». diff 읽기로는 못 본다 — 패키지 하나가 끌고 온 의존(예: `rsync` → `libssl3`)이 빌드 단계와 어긋나도 빌드는 초록이고, 머지 뒤 새 파드가 시드 단계에서 CrashLoop 해 남의 배포까지 막는다(2026-10-12 배포처 #527). 이미지를 못 빌드하는 환경이면 «미검증»으로 증적에 적는다.
- ★**리뷰어가 «기동조차 못 했으면»(에이전트 0회·빈 응답) 미검증이다** — 발견 없음이 아니다. 그때는 `/code-review high`. 도구 미지원이면 한계를 밝히고, 독립 리뷰를 자체 리뷰로 대체하지 않는다.

### 큰 워크플로 `merge-review` 는 위험 변경만
- 쓴다: **인증·권한·세션·비밀값** · **DB 마이그레이션** · **공용(`src/shared`) 계약 변경** · **배포 설정**(`k8s/**`·CI 배포 잡). CLAUDE.md '머지 등급'의 고위험 유형 중 **되돌려도 피해가 남는 것**이다.
- **크기만으로 키우지 마라** — 실측상 큰 리뷰가 앱 코드에서도 사소한 것만 냈다. 파일이 많아도 위 유형이 아니면 단일 리뷰다.
- 호출: Workflow 도구, 이름 `merge-review`, args **객체 그대로** `{base, card, externalSurface, level}` — ⚠️**JSON 문자열로 감싸 넘기지 마라**(한글이 깨져 렌즈가 0턴으로 끝난다 — 2026-09-18 배포처 #324 실측. 「감싸도 가드가 풀어 준다」는 서술을 믿지 마라)(렌즈 3개 병렬 + `externalSurface` 면 보안 렌즈 1개 더 + 발견마다 반박 3표). `merge-review` 가 기동 실패해도 `/code-review {level}`.

### 기록 칸 — 방식과 무관하게 필수 (2026-09-16)
- 방식(단일/merge-review) · 리뷰어 수 · 시간 · 토큰 · 확정 건수(사소한 것은 따로) · 기각·미해결 · **결함 위치**(`대상` = 카드가 고치려던 코드 / `비계` = 그 세션이 스스로 덧붙인 검사·안내) · 수정 횟수. **모르면 «미제공»** — 0 으로 적지 마라(안 적힌 것과 0건은 다른 값이다). 경과 시간은 워크플로가 안 주니 호출한 쪽에서 잰다.
- **증적 댓글을 올리기 «전에» 본문을 파일로 쓰고 `bash scripts/check-review-record.sh <본문파일>` 을 돌려라** — 여섯 칸 중 값도 «미제공» 도 없는 칸이 있으면 종료 1 로 칸 이름을 댄다(채운 뒤 다시). 칸은 `·` 로 이어 적어라(옆 칸 숫자를 값으로 읽는 것을 막는다). 근거: 10-13 재측정에서 토큰 37%·결함 위치 12%만 적혀 있어 «리뷰가 카드 본래 코드의 결함을 잡았나»를 가를 수 없었다. 이 검사는 CI 잡이 아니다(댓글은 저장소에 없다) — 부르는 쪽이 이 문장이다.

- ★★**리뷰가 도는 동안 HEAD 를 건드리지 마라 — 문서 커밋도 안 된다.** 리뷰는 «어느 판을 봤나»를 기준 커밋으로 들고 도는데, 그 사이 커밋이 하나 끼면 **리뷰 결과가 지금 판의 것이 아니게 된다**(배포처는 이 대조가 게이트라 설명문 한 줄 때문에 판정이 깨졌다 — 2026-09-18 #324). 남길 커밋은 **리뷰가 끝난 뒤** 한꺼번에.

### `merge-review` 를 쓸 때의 수준 (2026-09-10 개정 · 아래 경위는 그대로 유효)
★**결론부터**: `/done` 자체는 `medium`, **`merge-review` 의** 리뷰 수준은 **diff 가 정한다** — `고위험`·`k8s/**`·인증·권한·결제·마이그레이션이면 `high` · **`*.md` 만이면 `low`** · 그 밖은 `medium`(2026-09-30 Opus 5.5 기준으로 한 단씩 내림). 표와 근거 = `_reference/skill-tiers.md` §리뷰 수준.
- **왜 뒤집혔나(2026-09-10)**: 오너가 **세 번째로** 같은 말을 했다 — 「done이 xhigh라서 너무 오래걸리고 토큰 많이써 … 러프한 수정이면 러프하게 리뷰하도록 해」. 앞의 두 번을 이 문서가 반대로 옮겼다: 9-08 엔 「AI 가 낮게 굳힌다」를 이유로 **전부 xhigh 로 못 박았고**, 9-09 엔 오너의 「너무 단순하게 개선하려는 것 같다」를 **「낮추지 마라」로 읽고** 고정을 더 굳혔다(그 말은 «손잡이를 수준 하나로 단정하지 마라»였지 «낮추지 마라»가 아니었다). ★교훈: **같은 요청이 두 번째로 오면 «내가 지난번에 반대로 옮기지 않았나»부터 봐라.**
- **9-08 의 「AI 는 effort 를 판정하지 않는다」는 그대로 유효하다** — 뒤집힌 것은 «누가 정하나»가 아니라 «무엇으로 정하나»다. 부사(「가볍게」)는 여전히 금지고, 대신 `git diff --name-only` 한 번으로 답이 나오는 표를 쓴다.

### 경위 — 왜 한때 xhigh 고정이었나 (2026-09-08)
- 본문 리뷰 단계(당시 4단계, 지금 2단계)에 「기본 수준: /fix 커밋은 가볍게, /dev 커밋은 보통」이라고만 적혀 있었다(킷 첫 커밋부터, 설계 결정 기록 없음). AI 는 그 부사를 `low`·`medium` 으로 옮겼다 — bnsone 세션 기록 실측: `/code-review` 스킬 호출 70건 중 **low 20 · medium 20 · high 17 · 수준 없음 13 · xhigh 이상 0**. 수준을 안 적은 13건도 공식 문서상 «마지막에 친 수준을 재사용»이라 대개 low·medium 이었다.
- 공식 문서: low·medium 은 「가장 확신하는 발견만 보고해 오탐이 적은 대신 놓친다」, high~max 는 「넓게, 덜 확실한 것도 포함」. 오너 체감(「하나 고치면 다음 카드에서 또 거기서 수정사항이 나온다」)과 맞는다.
- 그래서 **effort 를 AI 가 고르게 두지 않는다** — 값을 문장에 박는다. 리뷰는 `/merge-review` 워크플로(렌즈 4개 + 반박 3표), 없으면 `/code-review xhigh`. `ultra` 는 사용량 크레딧 과금(회당 5~25달러)이라 금지(오너 결정 2026-09-08).
- ★**그런데 «얼마나 걸리나»가 안 쌓인다 — 그래서 끝나면 한 줄을 남긴다**(2026-09-09 추가). 실측: 설정 3줄 + 테스트 93줄짜리 카드에서 리뷰가 **10분 35초**(23:04:53 띄움 → 23:15:28 도착). 워크플로가 아니라 `/code-review xhigh` 단일 에이전트였는데도 그랬다. ⚠️**«백그라운드로 도니까 괜찮다»는 성립하지 않았다** — 세션은 17초 만에 다른 일로 갔지만 그 «다른 일»이 30초치뿐이라 **나머지 10분은 순수 대기**였다(리뷰가 마지막 단계라 겹칠 일이 없다).
- ⚠️**그렇다고 수준을 낮추는 쪽으로 가지 마라 — 그 리뷰가 진짜 회귀를 잡았다**(설정 한 줄이 `--testTimeout` 명령줄 옵션을 무력화했고, 세션이 직접 재현해 확인했다). 손볼 곳은 «수준»이 아니라 «탐색 범위»다: 이 워크플로의 렌즈 프롬프트는 «필요하면 파일을 열어 주변 코드를 확인하라»로 **한계가 없다.**
- **그래서 먼저 재라**: 반환값 `checked_files` 의 개수와 걸린 시간을 카드 증적에 한 줄로 남긴다. **«바뀐 파일과 그 호출부까지만»으로 범위를 좁히는 건 이 값이 몇 번 쌓인 뒤에 정한다** — 2026-09-09 시점엔 44회 조회가 무엇이었는지 셀 수 없었다(그 세션이 끝났고 서브에이전트 기록은 로컬에 안 남는다 — bnsone 관련 475파일 전수에서 0건).


### 재리뷰는 언제 도나 (2026-09-16 bnsone 실측)
- ★**재리뷰는 «카드 대상 코드»가 바뀌었을 때만 돈다.** 확정 발견이 전부 «이번에 내가 새로 더한 검사·비계»면 고칠 게 아니라 **덜어낼 것**이다 — 가름선은 «새 파일이냐»가 아니라 **«안 고치면 무엇이 깨지나»**(제품·절차가 깨지면 고친다). 실측: 그 nit 로 회차를 늘려 리뷰 5회·197만 토큰·52분을 썼고 카드 대상 결함은 1차 1건뿐이었다.

## §10 커밋 메시지 검사를 3단계에서 다시 보는 이유 (2026-09-09)

- ★**1단계에서 판정한 «커밋 메시지 검사»(bnsone `change-summary`)를 3단계에서 다시 확인한다.** 2단계 리뷰 반영으로 규칙·절차 문서(`docs/00_Guide/**` 등)를 **추가로** 건드렸으면 1단계에서 안 걸리던 경로가 새로 걸린다. **공통 영역 목록엔 그 경로가 없다** — 3번 줄만 보면 몰라서 지나간다.
- 이미 머지 직전에 걸렸으면 **새 커밋 하나를 더한다**(force push 불요).
- 이 절은 원래 `SKILL.md` 5단계 본문에 있었는데 **스킬이 컴팩션 한도(5,376자)를 넘기지 않도록** 여기로 옮겼다(2026-09-09 저녁3). 넘으면 스킬 뒤쪽이 통째로 안 읽힌다 — 이제 차단형 `skill-size` 잡이 막는다.

## §11 6단계 — `npm test` 가 안 돌리는 두 가지 (2026-09-28)

- **`.gitlab-ci.yml` 을 바꿨으면 `glab ci lint`** — 무효 CI 는 테스트가 못 잡는다(#72).
- ★**`scripts/` 를 바꿨으면 검사기 자기시험도 로컬에서 돌려라**: 저장소 루트에서 **`bash scripts/run-self-tests.sh`**(CI `self-tests` 잡이 부르는 것과 같은 스크립트 · 0 = 통과 · 1 = 실패 · 2 = 시험 0개라 판정 불능). 반복문을 직접 치지 마라 — 묶음 훅이 되돌려 보낸다. `npm test` 는 앱 테스트(vitest 류)만 돌리고, `scripts/test-*.sh` 는 CI `self-tests` 잡만 모은다 — **로컬 초록인 채 머지 전 리뷰나 CI 에서야 걸린다**(bnsone #315 리셋 스크립트 자기시험 결함 · #347 `check-failclosed` 누락 — 같은 모양 두 번).
  - ⚠️**실패가 나면 «내 변경 탓인가»를 `main` 기준선과 비교해 갈라라** — 임시 워크트리(`origin/main`)에서 같은 스크립트를 돌려 실패 수가 같으면 기존 실패다(`종료코드 0 = 통과` 만으로는 못 가른다). Windows 에서 `run-self-tests.sh` 7개가 main 에서도 실패한 적이 있다(bnsone #300 — 수 9/8·10/10·27/21·4/14·25/1·13/1·19/1). 기준선과 같으면 카드에 «기존 실패, 내 변경 무관» 한 줄과 스크립트 이름을 남기고 진행하라.
  - ⚠️**CI 잡에는 `GATE_API_TOKEN`·`CI_*` 변수가 이미 들어 있다** — 가짜 CLI(`glab` 등)로 도는 새 시험은 그 변수를 비운 채(`env -u …`) 한 번 더 돌려 보라. 로컬 초록·CI `self-tests` 빨강이 난다(bnsone #773 실측).
  - ⚠️**워크트리에 `node_modules` 가 없으면** `yaml` 을 쓰는 시험이 `Cannot find module 'yaml'` 로 빨갛다(코드 결함처럼 보인다) — 그 트리에서 `npm ci`(울타리 밖) 뒤 돌리거나 같은 판의 본 클론에서 돌려라. `check-skill-size.sh`·`check-density.sh` 는 **검사할 폴더에서** 불러라 — 다른 폴더에서 부르면 그 폴더를 검사해 «OK» 가 난다(bnsone #826 실측).
