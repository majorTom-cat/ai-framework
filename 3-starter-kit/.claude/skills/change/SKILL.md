# /change — 요구사항 변경 반영

> **계약** · 입력: 변경 요약/바뀐 docs · 산출물: docs 정본 먼저 수정 + 영향 카드 신규·수정·무효 · 검증: docs diff + 카드 정합 (⏸ 실행 전 확인)

> **예시**: `/change 익명 게시판 기능 삭제` · `/change docs/03_Requirement/게시판.md` (여러 단어를 따옴표 없이 그대로 쓰면 된다).

**이 스킬을 쓰면 안 되는 경우**: 요구사항(docs 정본)은 그대로인데 구현이 틀린 것 = 버그 → `/fix`. /change 는 **정본이 바뀔 때**만.

변경 내용: $ARGUMENTS (비어 있으면 docs/의 최근 변경을 `git log -p -3 -- docs/` 로 파악)

0. **변경 카드 발행**(번호 확보) — 이후의 docs 수정 커밋은 이 번호로 한다. 영향 분석 표(1번)도 이 카드에 기록
   — ★**발행 전에 중복부터 본다**: 같은 정본 개정을 이미 처리한 변경 카드가 있는지 `glab issue list --all`로 대조하라(있으면 새 카드 대신 그 카드에 잇는다).
     **`--search`의 한국어 부분일치는 안 잡힌다 — 0건을 부재의 근거로 쓰지 마라**(제목을 눈으로 훑어라). 열린 카드 검색이 1번에만 있으면 **발행한 뒤**라 이미 늦다(2026-08-18 중복 발행 실측).
   — **docs가 이미 수정·커밋돼 있던 경우**(공통 개발자의 초기 정비 등): 소급 연결한다 — 그 커밋 해시를 변경 카드 본문에 기록
1. **영향 분석 표**를 만들어 보여줘라:
   | 영향받는 것 | 현재 상태 | **상위 정본이 수용했나** | 제안 |
   - ★★**«상위 정본이 수용했나» 칸을 비운 채 넘어가지 마라** — 하위 문서(모듈 업무설계 등)만 읽어도 나머지 칸은 채워지므로, 이 칸이 없으면 **하위 정본이 상위 정본의 미결을 닫아 버린다**(2026-09-09 bnsone 실측 2건 — 한 세션에서 두 번). 확인법 = 상위 STEP 정본의 «미결·질문» 목록에 그 항목이 아직 남아 있나(남아 있으면 **아직 안 닫혔다** — 하위 문서에 결론이 적혀 있어도 그렇다).
   - 관련 **모듈** (어느 소유자 관할인가)
   - **차터(00_Project)가 바뀐 변경이면**: 설계 전제(플랫폼·스택·DB — /design ①~④)가 여전히 유효한지 재검증을 영향 분석에 포함 — 흔들리면 `/design` 재실행 카드를 발행 (차터 변경은 요구 변경보다 파급이 큰데 트리거가 조용하다)
   - **열린 카드** (glab 검색) — 내용 수정 필요? 무효?
   - **진행중 카드** — 있으면 해당 카드 댓글 + 담당자 @멘션 제안
   - **이미 구현된 코드** — 수정 카드 / 제거 카드 필요?
2. 변경 유형별 제안 규칙:
   - 추가 → 반나절~이틀 크기 **새 카드** 초안(제목·설명·담당자). **고위험 판정**: CLAUDE.md '머지 등급'의 고위험 유형(정본 = 그 절)을 새로 건드리면 `고위험` 라벨(/card와 동일 기준 — 요구 변경발 고위험이 여기서 잡힌다)
   - **열린 카드의 내용이 바뀜** → 카드 본문 수정 + 변경점 댓글 + 담당자 @멘션. 카드가 **`검수요청` 상태면 검수자에게도 @멘션**(재검수 대상 — 옛 기준으로 닫히는 것 방지). **방향 자체가 바뀌면** 무효+신규(제목에 "(#원번호 대체)")
   - 무효가 된 카드 → **`무효` 라벨 추가 + 상태 라벨(`진행중`·`검수요청`) 제거 + 닫기** (라벨 add/remove는 별개 — 상태 라벨이 남으면 /metrics가 왜곡된다) (사유 한 줄, 삭제 금지) + **담당자 @멘션 필수** — 조용히 닫으면 담당자의 /todo 에서 카드가 소리 없이 증발한다. **이미 완료됐던 카드면 사유에 "완료였음(날짜)" 병기** — 정상 완료 이력 보존
   - 완료된 카드의 후속 수정 → 새 카드, 제목에 "(#원번호 후속)" + 관련 이슈 링크(glab)로 연결. 수동 하위번호(12.1) 금지
   - **기능 삭제** → 순서 정본 = CLAUDE.md '변경·삭제' 절 — 그 3순서(플래그 off→코드 제거→스키마 drop)를 **카드 3장으로** 발행 + docs 절은 Removed 표시(서식 정본 = rules/docs.md)
   - **되돌리기 어려운 결정을 뒤집는 변경**(DB·모듈 경계·공개 계약·플랫폼) → **`/adr` 로 대체 ADR 기록**(옛것 "대체됨 → 새 번호", INDEX 갱신까지 /adr이 처리 — 여기서 직접 쓰지 말고 위임). 규모가 크면(스택·구조 통째) **`/design` 재실행**으로 넘긴다 — 이게 없으면 다음 세션 AI가 옛 방향으로 "복원"한다
3. **⏸ 사용자(기획자·공통 개발자) 확인 후** 실행 — 순서: **①먼저 docs 정본 수정**(변경의 정본은 docs다 — 아직 안 바뀌었으면 지금, 0번의 변경 카드 번호로 `#{변경카드번호} docs: …` 커밋. 이건 glab 이슈 조작과 별개의 git 커밋이다). **②그다음** 카드 생성·수정·닫기·멘션을 glab으로 처리
   — ★**연쇄 갱신 체크리스트 — 요구 하나를 고치면 문서 여러 곳이 따라 바뀐다**(본문만 고치면 나머지가 어긋난다: bnsone 요구 2건 추가에 fresh 리뷰 Critical 2+Important 6, 전부 이 유형). 문서마다 이름이 다르니 **해당하면** 갱신, 안 하면 "없음" 명시(빈칸 금지):
     □ 그 항목이 속한 **표의 머리 숫자**(예 "예약 (9건 — 1차 3…)")  □ **요약 수치표**(영역·차수별 합계 — 직접 세어 검산)  □ **추적성/매핑 표**  □ **개발팀 전달용 요약 절**  □ **변경 이력 표**(행 추가)
     □ **`_digest.md`·`docs/_STEP_INDEX`**(지도가 낡으면 /design·/dev가 옛 지도로 간다)  □ **앞선 STEP 정본과 충돌 → 대체됨 표지판**  □ **제약사항 절**(새 요구를 막는 제약이 있나 — "신규 시스템·마이그레이션 없음"이 새 이관 요구를 부정한 사례)  □ **번호 체계**(그 문서 형식을 따르되 하위번호 신설 금지)
   — ★**일괄 치환 후엔 `grep`으로 확인**한다 — 옛 이름과 새 이름이 한 문장에 같이 있던 곳이 같은 이름 두 번으로 깨진다(제품명 치환이 `BNSOne/BNSOne` 4곳 생성 — 실측)
   (실행자가 곧 결정권자[기획자 본인]면: 영향 분석 표를 변경 카드에 남기는 것으로 확인을 갈음하고 진행)
4. 마무리 보고: 정리 결과(신규 N·수정 N·무효 N) + **"새 카드 착수는 `/dev {번호}` 또는 `/fix {번호}`"** — 다른 담당자 카드는 멘션이 갔으니 그들의 /todo에 뜬다.
   **변경 카드 자체는** "화면 없는 카드" 규칙(상태 전이표)대로 정리 증거 댓글 + **`셀프완료` 라벨 전환** 후 셀프 완료(라벨이 기록 정본 — 절차는 /done 8단계)

## ❌ 금지 — 그 순간 드는 핑계와 반박까지

- 확인 없이 카드를 닫거나 만들기 · docs 절 통째 삭제(Removed 표시로) · 진행중 작업을 임의로 중단시키기

| 하고 싶어지는 말 (핑계) | 반박 |
| --- | --- |
| "간단한 변경이니 코드부터 고치고 카드는 나중에" | 번호 없는 커밋·docs 수정은 추적 불가가 된다 — 카드 발행은 30초, 유실된 이력 복구는 며칠 (0번이 첫 단계인 이유) |
| "이 카드는 이제 필요 없으니 삭제하자" | 삭제는 이력 파괴다 — `무효` 라벨+닫기로 사유를 남겨야 나중에 "왜 없어졌지"에 답할 수 있다 |
