# /ui — 화면 UI 완성도 있게 만들기

> **계약**
> - 입력: 이슈번호/화면명 · 산출물: 프론트 코드(diff) · 검증: /inspect+상태3종

> **예시**: `/ui 12` (보통 화면 카드에서 `/dev`가 자동 호출)

## 진입 판정 — 만들기 전에

- **시안 모드는 폐지됐다**(오너 결정 2026-10-15) — `시안 …` 인자를 받으면 만들지 말고 "시안은 없앴다 — 확정 디자인이 없으면 설계서+공통 부품으로 바로 만든다"고 알린 뒤 구현으로 돌려라. 시안부터 하라고 권하지 마라.
- **확정 디자인 소스**(기획자가 준 디자인 문서·`docs/05_UIUX/screens/{화면}/` 의 기존 파일)가 있으면 그것이 정본이다. **없으면** 요구사항+디자인 시스템으로 직접 설계하고 **카드 댓글에 «확정 디자인 없음» 한 줄**을 남겨라(기록이 없으면 다음 세션은 빠뜨린 것으로 읽는다).
- 화면 코드가 `src/` 에 이미 있는데 화면명만 받았으면 수정 요청인지 한 줄 확인.

## 0. 먼저 — 우리 디자인 시스템을 읽어라 (일관성의 핵심)
- **`<디자인시스템 위치>`**(예: `src/shared/ui/` · `docs/05_UIUX/design-tokens.md`)를 먼저 읽는다: 색·타이포·간격 토큰, 공용 컴포넌트, 브레이크포인트, 쓰는 프레임워크(`<UI프레임워크>`).
- **아직 없으면**(초기 화면): 지금 화면을 근거로 **최소 토큰·공용 컴포넌트·프레임워크를 먼저 정해** `docs/05_UIUX/design-tokens.md` + `src/shared/ui` 에 씨앗을 심는다 — 그래야 다음 화면들이 여기서 안 벗어난다. (shared 변경이니 착수 전 채팅 공지.)
  - **심었으면 통로도 같이 만든다**: 그 정본을 가리키는 한 줄을 «항상 읽히는 층»(루트 CLAUDE.md 또는 `paths:` 없는 rules 파일)에 넣어라 — 안 넣으면 다음 세션은 그 문서가 «없다»고 답한다(CLAUDE.md '정본을 새로 만들면 통로도').

## 1. 이 화면의 방향 (frontend-design 원칙 — 단, 시스템 안에서)
- 목적·사용자·주요 동작을 한 줄로. 이 앱은 **업무용**(중소기업 직원 다수) — 화려함보다 **명료·빠름·모바일**이 먼저.
- 그 안에서 완성도를 올린다: 뚜렷한 **타이포 위계**, 넉넉한 간격·정렬, **모든 상태(로딩·빈·에러·성공)**, 명확한 1차 액션, 접근성 기본(대비·키보드 포커스·라벨·터치 타깃 44px).
- **카피도 디자인이다**: 버튼은 일어날 일 그대로("변경 저장" ○ / "제출" ✕), 같은 동작은 흐름 내내 같은 이름(저장 버튼 → "저장됨" 토스트), 에러는 사과·모호 없이 **원인+해결**, 빈 화면은 다음 행동 안내 — 시스템 용어가 아니라 사용자 언어로("웹훅 설정" ✕ / "알림 관리" ○).
- **폼 오류는 지속되는 글자로**: 브라우저 네이티브 안내(`reportValidity`·`title`)에만 기대지 마라 — 사파리 등에서 안 뜬 채 «게이트 초록»으로 지나간 사건(bnsone #808). 오류 문구를 화면 안 글자로 계속 보이게 · 첫 오류 칸에 포커스 · 칸과 문구를 `aria-describedby`·`aria-invalid` 로 잇는다(꼭 칸 아래일 필요는 없다). 서버 오류 코드 변환 규칙과는 별개.
- ⛔ **밋밋한 AI 기본값 회피**: 시스템 폰트 그대로·의미 없는 카드 나열·상태 없는 화면 + **AI 상투 3종 수렴 금지** — ①크림 배경+세리프 제목+테라코타 포인트 ②흑배경+형광 단색 포인트 ③신문형 헤어라인 격자. 셋 다 '선택'이 아니라 '기본값'이다(Anthropic frontend-design이 실측 정리한 현재 상투 — 주제와 무관하게 이 셋이 나오면 기본값에 끌린 것).
- 화면마다 미학을 제멋대로 바꾸지 마라 — **일관성 > 개별 플레어**. 바꾸려면 시스템(shared)에서.
- (플러그인 `frontend-design`이 설치돼 있으면 이 단계에서 그 접근을 활용해도 좋다 — 없어도 위 원칙으로 충분하다.)

## 2. 만들기 — 공용부터, 모바일부터
- **`src/shared/ui` 공용 컴포넌트를 먼저 쓴다.** 없어 새로 만들면, 2개 이상 모듈이 쓸 것은 **shared 승격 제안**(CLAUDE.md 소유 경계 규칙).
- **모바일 우선**(charter: 모바일 전체 지원): 375px에서 먼저 설계 → 넓은 화면으로 확장.
- **무료 UI 프레임워크·템플릿만**(charter 제약) — 유료 에셋 금지.
- 본보기 모듈(`src/modules/<본보기모듈>`)의 화면 패턴이 있으면 그것을 먼저 베낀다.

## 3. 만든 뒤 — 반드시 검사로 넘긴다
- **`/inspect $0`**: 반응형(375px)·가로 넘침·콘솔 에러·인터랙션·이상 입력 (디자인 소스 있으면 대조).
- **상태 3종(빈·로딩·에러)이 실제로 렌더되는지** 눈으로 확인. 안 보이면 아직 안 끝난 것.

## ❌ 금지 — 핑계와 반박
| 핑계 | 반박 |
| --- | --- |
| "일단 되게만, 디자인은 나중에" | 나중은 안 온다(디자이너 없음) — 만들 때가 완성도의 유일한 기회 |
| "이 화면만 좀 다르게 하고 싶다" | 여럿이 만드는 앱에서 개별 미학 = 누더기. 바꿀 거면 shared에서 전체로 |
| "데스크톱에서 잘 보이니 됐다" | charter는 모바일 전체 지원 — 375px가 1차 기준 |
| "빈/에러 상태는 흔치 않으니 생략" | 실사용 첫날 바로 나오는 상태다 — 상태 없는 화면은 미완성 |
