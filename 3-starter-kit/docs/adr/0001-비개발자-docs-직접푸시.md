# ADR-0001: 비개발자(기획/디자이너)는 `docs/`를 직접 편집·커밋한다 (길 A)

- **상태**: 채택
- **날짜**: 2026-07-13
- **결정자**: 공통 개발자

## 배경 — 왜 결정이 필요했나
기획/디자이너가 만든 문서(요구사항·시안)를 정본(`docs/`)에 반영하는 경로가 필요하다.
초기 설계(길 B)는 "비개발자 = Reporter, docs는 **카드로 요청** → 개발자/AI가 `/docs`·`/change`로 대신 반영"이었는데,
문서 한 줄·오타 하나까지 매번 개발자/AI를 거쳐야 해 **병목**이 생겼다.

## 결정
비개발자(기획/디자이너)에게 **`Maintainer` 권한**을 부여하고, `docs/`를 GitLab 웹에서 **직접 편집·커밋**하게 한다(길 A). 코드에 영향이 있으면 카드도 함께 남긴다.
- 브랜치 모델은 **트렁크 기반**(feature → main 셀프 머지, develop 없음). **main 보호(MR 전용) + Pipelines must succeed**가 켜지면 비개발자의 docs 변경도 MR로 흐르고, 본인이 셀프 머지한다(Maintainer라 가능).
- **초기 폴더 뭉치(하위폴더 있는 문서 묶음)** 는 예외: GitLab 웹이 폴더 구조 유지 업로드를 못 하므로 **1회만 공통 개발자가 clone에 풀어 배치**(`/docs`)하고, 이후 단일 문서 편집은 웹에서 직접 한다.
- **권한 수준**: 지금은 팀 신뢰 기반으로 `Maintainer`로 시작한다. 최소권한 관점에선 `Developer`가 이상적이므로, 신뢰 전제가 바뀌거나 팀이 커지면 `Developer` 하향 + `planner-guard` 활성화를 재검토한다(아래 "감수하는 것").

## 검토한 대안
- **길 B (Reporter + 카드로 요청 → AI 반영)** — 문서 변경마다 개발자/AI 병목. 자율성·속도가 떨어져 기각.
- **경로별 사전 차단 (CODEOWNERS / Push Rules로 "docs만 허용, 코드 보호")** — 사내 GitLab은 **Community Edition**이라 이 기능이 유료 Premium 전용. **사용 불가**라 기각.
- **Developer 권한 + planner-guard 즉시 활성화** — 최소권한으로 더 안전하나, 현재는 `Maintainer`로 시작하기로 함(팀 규모·신뢰). planner-guard는 옵션으로 남겨둠(추후 승격 가능).

## 감수하는 것
- `Maintainer` + CE(경로 보호 불가)이므로, **비개발자가 권한상 코드·`.gitlab-ci.yml`·프로젝트 설정까지 건드릴 수 있다.** 이를 100% 사전 차단하는 수단이 없다.
- 실수 방어는 **① 가이드 명시("비개발자는 `docs/`만") ② main 보호(MR + CI) — 코드 변경은 CI가 검사 ③ (옵션) `planner-guard` CI 사후 감지 ④ "main 깨지면 revert 최우선" 규율** 에 의존한다.
- 위 안전망 중 **main 보호는 아직 미적용**(2026-07-13 기준 `protected_branches` = 없음). 개발자들이 코드를 밀기 시작하기 전에 켜야 한다(공통 개발자 가이드 Day 2). 그전까지는 트렁크 기반의 자동 안전망이 비어 있다.
- 신뢰 전제가 깨지거나 팀이 커지면 → `Developer` 하향 + `planner-guard`(`PLANNER_EMAILS`) 활성화로 조인다. 그때 이 ADR을 새 번호로 대체한다.
