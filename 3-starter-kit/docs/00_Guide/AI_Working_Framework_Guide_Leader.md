## 0. 공통 개발자가 처음이라면 — 시작 전 5분 (겁먹지 마세요)

### 🧭 공통 개발자는 뭐 하는 사람?
**팀이 올라탈 "레일"을 까는 사람**입니다. 레일이 깔리면 개발자들은 각자 AI로 그 위를 달려요. 당신 일은 딱 둘:
- **첫 주(골격 주간)** — 레일을 깐다 (아래 Day 0~6).
- **그 뒤** — 하루 10분 지켜보고, 문제가 생기면 대응한다 (3절).

### 😌 겁먹지 마세요 — 대부분은 킷이 이미 만들어놨습니다
이 프로젝트는 **스타터 킷을 복사해 시작**했어요. 그래서 규칙(`CLAUDE.md`)·**스킬 19개**(개발 13 + 공통 개발자 6)·훅·권한 설정이 **이미 들어 있습니다.** 당신이 맨땅에서 만드는 게 아니라:
1. **정한다** — 어떤 기술로 만들지 (Day 0)
2. **채운다** — 킷의 빈칸(`<기동명령>` 같은 것)을 이 프로젝트 값으로
3. **눈으로 확인한다** — 실제로 앱이 뜨고, 검사가 돌고, 배포되는지

### 🗺️ 전체 그림 — 하루에 하나씩
| Day | 한마디로 | 끝난 신호(눈으로) |
| --- | --- | --- |
| 0 | 뭘 만들지 정하기 (요구사항·기술) | "이 스택·DB로 짤 수 있다"가 명확 |
| 1 | 앱 뼈대 세우기 | **빈 앱이 브라우저에 뜬다** |
| 2 | 자동 검사(CI) + GitLab 설정 | MR 만들면 검사 돌고, 머지하면 배포된다 |
| 3 | 규칙 채우기 (CLAUDE.md 빈칸) | "규칙 요약해봐"에 우리 규칙이 나온다 |
| 4 | 강제 장치 켜기 (훅) | shared 고쳐 push하면 **경고가 뜬다** |
| 5 | 시드(seed — 화면 확인용 초기 데이터) + 예행연습(파일럿) | 카드 하나가 등록→배포까지 막힘없이 돈다 |
| 6 | 본보기 기능 하나 완성 | 다른 개발자가 그걸 베껴 두 번째를 만든다 |

각 Day는 **"만들었다"가 아니라 "직접 돌려서 눈으로 봤다"** 가 완료예요. 서두르지 말고 하루에 하나씩.

### 📖 이 가이드 쓰는 법
- **이 문서엔 네 종류가 섞여 있어요** — 표시로 구분하세요: 🎯 그 Day의 **목표 한 줄** · 📖 그냥 **읽는 설명** · 💻 **명령** = 그 단계에서 치는 것(대부분 스킬 하나) · `★` = **깊은 근거**(궁금할 때만). **상세 내용물은 문서에 안 싣습니다** — 킷 실물과 스킬이 정본이고, 이 가이드는 순서·확인 기준만 담아요.
- 어디까지 했는지 헷갈리면 → repo에서 `claude` 켜고 **`/start`** — 공통 개발자 모드가 Day별 상태를 진단해 "다음은 Day N"을 짚어줍니다.
- **당신도 개발자처럼 스킬로 일해요**: `/dev`·`/done` 등. 자연어로 "이거 해줘" 하면 AI가 맞는 스킬로 안내해줍니다.

### 🧰 공통 개발자가 쓰는 스킬 — 붙여넣기 대신 "명령으로"
개발자가 `/dev`·`/done`을 쓰듯, **공통 개발자의 반복 셋업도 스킬**로 합니다 (긴 프롬프트 붙여넣기 ❌):

| 스킬 | 언제 | 예시 | 무엇을 하나 |
| --- | --- | --- | --- |
| **`/design`** | Day 0 (요구 문서 올라온 뒤) | `/design` | 요구 → 설계 제안 → 공통 개발자 결정 → `docs/06`+ADR |
| **`/scaffold`** | Day 1 (설계 후) | `/scaffold` | 앱 뼈대·CI·CLAUDE.md 빈칸 생성 |

> 인자 없는 것(`/design`·`/scaffold`·`/setup-gitlab`)은 실행하면 **대화로 값을 물어봅니다**. 공통 개발자도 쓰는 개발 스킬 예시는 아래 Day별 안내 + `/dev 12`(파일럿)·`/card 게시판 목록 만들기`·`/done 12`·`/module board` (전체는 ONBOARDING·README 표).

**순서**: **`/design`**(요구→설계·공통추출) → **`/scaffold`**(뼈대) → **`/setup-gitlab`**(GitLab) → (Day 3~4 킷 빈칸 채우기·확인) → 파일럿(사소한 카드 1개를 `/dev`로) → (Day 6 본보기 = `/module` + `/dev`).

**변수 상황엔 이렇게**:
- **Day 0 설계가 아직**이면 → `/scaffold`가 "설계부터 하세요" 하고 멈춥니다 (감으로 안 만듦).

- **스택을 바꾸기로** 하면 → 설계(`docs/06_TechnicalDesign`)를 고치고 `/scaffold` 다시.
- **결정(스택 선택 등)은 스킬이 대신 못 합니다** — `/design`이 근거와 함께 안(案)을 주면 **당신이 게이트에서 고르는** 것(잡담이 아니라 '선택'). 모든 걸 스킬로 하진 않되, 요구 분석·기록 같은 절차는 스킬이 합니다.

## 1. 골격 구축 — Day 0~6 (준비 Day 0 · 골격 Day 1~5 · 본보기 Day 6)

**우선순위 원칙:** P1이 안 되면 팀 착수 금지. P2는 첫 주 안에. P3는 운영하며 추가.

> ★**이 프로젝트는 스타터 킷(`3-starter-kit`)을 repo에 복사해 시작한다.** 그래서 아래 Day 3~6의 **`CLAUDE.md`·`.claude/rules`·훅·스킬 전부(개수·목록의 정본 = [repo README §4](/README.md#4-스킬--하나씩), Day 6 체크리스트에도 있음)는 이미 킷에 들어 있다** — "만들어줘"가 아니라 **① 플레이스홀더를 채우고(`<기동명령>`·`<검수서버URL>` 등) ② 스택에 맞게 연결하고 ③ 실제로 로드·동작하는지 검증**한다. 진짜로 새로 만드는 건 셋 — **Day 0 설계문서 · Day 6 본보기 모듈 · Day 4 강제 장치 일부**(husky 등 `package.json`이 생긴 뒤에야 만들 수 있는 것 — Day 4에 목록)뿐.
> 📦 **킷의 출처와 업데이트**: 원본 킷 = 사내 프레임워크 설계 홈의 `3-starter-kit`(이 repo 밖, 프레임워크 유지보수자 관리). **순수 프레임워크 파일(`.claude/skills`·`rules`)은 킷이 정본** — 개선은 킷을 먼저 고치고 각 repo에 복사(byte 동일)로 반영한다. `CLAUDE.md`·가이드처럼 프로젝트 값이 섞인 파일은 **로직만 동기**하고 채워진 값은 보존. 이 동기가 끊기면 낡은 프레임워크로 일하게 된다 — 프레임워크 변경 공지가 오면 반영 여부를 확인하라.
> 📎 **청사진·근거 문서는 킷에 동봉되지 않는다 — 프레임워크 홈(`ai-framework/`)에 있다.** 설계 청사진 `2-team-dev/AI_Working_Framework_Playbook_TeamDevMode.md` · Day 6 상세 `2-team-dev/AI_Working_Framework_Guide_GoldenPath.md` · 근거·출처 `4-reference/*.md`. **이 가이드로 충분하고, 그 문서들은 "왜?"가 궁금할 때만** 펼친다(프레임워크 유지보수자에게 요청하거나 프레임워크 repo에서 직접 연다).
> ※ repo에 복사되는 `_reference/`는 **다른 것**이다 — CLAUDE.md·CI가 본문에서 가리키는 실전 노트 전부가 들어 있다. 위 청사진·근거를 이 repo에서도 보고 싶으면 프레임워크 홈에서 `_reference/`로 복사해 오되, **사본을 늘리면 드리프트한다**는 점을 감수하라.

### Day 0 — 요구사항 정리 + 기술 설계 〔P1, 골격보다 먼저〕

> 🎯 **이 Day: "뭘 만들지"를 정한다.** 기획 요구사항을 읽고 → 어떤 기술(언어·DB·구조)로 만들지 결정. 여기서 나온 게 Day 1 뼈대의 재료예요. **감이 아니라 요구사항 근거로** 정하세요 — 여기가 틀리면 뒤에서 다 뜯어고칩니다.
>
> 💻 **예시**: `/docs inbox/받은문서.zip` (문서 정리) → `/design` (설계 제안)

> **📥 기획자가 문서를 올렸을 때 — 딱 이 순서:**
> 1. **`/docs <받은 폴더나 zip 경로>`** — 파일을 정본으로 정리한다(`docs/03_Requirement`·`docs/05_UIUX`, 원래 계층 보존·충돌 표시).
>    **기획자가 GitLab 웹으로 이미 `docs/`에 올렸으면**(=길 A — 비개발자가 웹으로 직접 올리는 경로, GitLab 가이드 §1·§7) 경로 없이 그냥 **`/docs`**. 어느 쪽이든 스킬이 하는 일은:
>    스킬이 배치 검토 → digest 생성 → `_STEP_INDEX` 갱신 → 다음 판단 안내까지 처리한다(상세 = `/docs` 스킬). **확인 기준: 인덱스가 ⏳로 남아 있으면 미완.**
> 2. **부족한 요구·플랫폼 질문을 기획자와 확인** — 특히 웹이냐 앱이냐 · GPS/오프라인/푸시 · 자체 서버·Docker 가능 여부. **요구는 기획자 몫 — 공통 개발자가 지어내지 않는다.**
> 3. **`/design`** — 요구를 읽어 플랫폼·스택·DB·모듈·공통을 2~3안 제안 → **당신이 게이트에서 결정** → `docs/06`+ADR 기록. 요구가 더 오면 **재실행**.
>
> ⚠️ **스택·DB가 지금 없는 건 정상** — 그게 `/design`의 *산출물*이다. `/design`은 "문서 정리"(그건 `/docs`)나 "css만 뽑기"가 아니라 **설계 전체를 한 묶음으로** 다룬다.

골격(Day 1)에서 스택·DB·모듈을 정하려면 **그 전에 받은 요구사항을 정리하고 기술을 설계**해야 한다. 이 앞단은 원본 프레임워크의 STEP 3(요구사항)~6(기술 설계)에 해당한다 — 건너뛰고 스택을 감으로 정하면 뒤에 재작업이 크다.

> ⚠️ **아직 요구사항이 없거나(차터만 있음), 조금씩 들어온다면** — `/design`은 요구사항 문서(`docs/03_Requirement/`)가 있어야 돈다. 없으면 멈추되 **스킬이 다음까지 안내한다**(첫 슬라이스 카드 요청 + 대기 중 미해결 질문 확정). 그럴 땐:
> - **차터(STEP 0)만 있으면** → 먼저 기획자와 STEP 1~5(요구사항)를 만든다. 최소한 **처음 만들 영역의 요구**라도. 그게 정본으로 올라온 뒤에 `/design`.
> - **스택을 가르는 미해결 질문 먼저 확정** → 예: 모바일 방식(반응형 웹/PWA/네이티브)·자체 서버·Docker 가능 여부·외부 시스템 연계 유무·기존 코드 재사용 여부. 이런 건 스택을 좌우하므로 **설계 게이트 전에** 기획자·인프라 담당과 정한다(차터 digest의 "미해결·질문"이 출발점).
> - **요구가 조금씩 온다면** → 다 기다리지 말고 **처음 슬라이스만 설계**해 착수하고, STEP 문서가 더 오면 `/design`을 **재실행**(스킬의 🔄 재실행 규칙)해 설계를 넓힌다. 반쯤 설계된 채 코드부터 나가는 게 최악.

**`/design`이 제안하는 결정 축은 6개** — ①플랫폼 ②스택 ③DB·ERD ④모듈 분할 ⑤shared 추출 ⑥비기능.
각각 2~3안 + 근거·트레이드오프로 온다. **축의 정의·부분 설계 규칙의 정본 = `/design` 스킬**이다 — 이 가이드 곳곳의 ⑤·⑥ 같은 번호 표기도 그 스킬 기준.

**당신이 게이트에서 결정**(감이 아니라 요구 근거로) → 스킬이 `docs/06_TechnicalDesign` + **ADR**에 기록(되돌리기 어려운 결정 — 다음 세션이 임의로 뒤엎는 걸 막는다). 요구가 더 오면 `/design` **재실행**.

**완료 기준:** `docs/03_Requirement` 정본 + `docs/06_TechnicalDesign`(스택·ERD·모듈 분할) + 핵심 결정 ADR이 있고, **"이 스택·DB·모듈로 Day 1 골격을 짤 수 있다"** 가 명확하다.

### Day 1 — repo + 앱 뼈대 + docker-compose 〔P1〕

> 🎯 **이 Day: 앱의 빈 뼈대를 세운다.** 아직 기능은 없어요 — 로그인 없이 **빈 화면이 뜨고**, `docker compose up` 한 줄로 켜지는 것까지.
>
> 💻 **예시**: `/scaffold` (인자 없이 — Day 0 설계를 읽어 뼈대를 만든다)

**먼저 결정할 것:** 기술 스택·마이그레이션 도구·모듈 이름·소유자 — **이건 Day 0의 기술 설계(`docs/06_TechnicalDesign`·ADR)에서 이미 나온 결정**을 그대로 쓴다(Day 0을 건너뛰었다면 지금 감으로 정하지 말고 Day 0부터).

▶ **`/scaffold` 를 실행하세요.** Day 0 설계(`docs/06_TechnicalDesign`)를 읽어 **src 구조(모듈은 index만 노출) · docker-compose(db→migrate→app) · CI test·boundaries 활성화 · 플래그+`?preview` 미들웨어 · 버전 푸터 · reseed 스크립트 · CLAUDE.md 빈칸**까지 다 만듭니다. 붙여넣을 프롬프트 없음 — 내용물의 정본은 `.claude/skills/scaffold/SKILL.md`.

**⚠️docs/ 디렉터리 = 킷 뼈대로 고정** — 폴더 구성·배치 규칙의 **정본 = `/docs` 스킬**(여기서 벗어나면 `/docs`·`/card`가 문서를 못 찾는다). 공통 개발자가 기억할 것은 **쌓임 정책**뿐:

> **문서가 무한정 커지지 않는 유일한 이유 = "정본은 현재 상태만, 이력은 git·카드"**. 요구가 바뀌면 새 파일을 만들지 말고 그 파일을 고쳐라(없어진 요구는 "Removed" 한 줄 — 변경 경위는 카드·git이 안다). 예외는 `docs/adr/`(append-only — 뒤집으면 새 파일+옛것 "대체됨" 표시)과 `docs/inbox/`(임시 수신함 — `/docs`가 정본 배치 후 치움)뿐이다. 한 파일이 너무 길어지면 파일 수를 늘리기보다 구조를 정리한다.

> ⚠️ **repo 초기화 함정 2개** (드라이런 실증 — 합류자 전원이 첫 clone에서 fatal): ①기본 브랜치가 main인지 확인 (`git config init.defaultBranch` 가 master인 머신이 있다) ②self-hosted에서 bare/미러 repo를 직접 만들면 `git symbolic-ref HEAD refs/heads/main` 으로 **HEAD를 main에 지정** — 안 하면 모든 clone이 "remote HEAD refers to nonexistent ref" 경고·일부 명령 fatal.

### Day 2 — CI/CD + GitLab 설정 〔P1〕

> 🎯 **이 Day: 자동 안전망(CI)과 GitLab을 켠다.** 사람이 코드리뷰를 안 하는 구조라 **이 자동 검사가 유일한 안전망**이에요 — 그래서 필수(P1). CI(자동 검사) + main 보호 + 라벨 + 멤버 초대까지. **개발자가 코드를 밀기 전에 이게 켜져 있어야** 합니다.
>
> 💻 **예시**: `/setup-gitlab` (인자 없이 — 값은 대화로 물어봄)

> CI(`.gitlab-ci.yml`)는 **킷에 골격판이 있고, `/scaffold`가 스택에 맞는 `test`·`boundaries`를 채워 활성화**합니다. **잡 목록·차단/경고 구분의 정본 = 킷 `.gitlab-ci.yml`과 그 주석** — 여기 옮겨 적지 않습니다. **정책 3개만 기억하세요:**
> - 시크릿 스캔처럼 확실한 것은 차단, 오탐 여지가 있는 것은 경고 — 특히 "src·test 동시 수정=변조" 같은 파일 규칙은 **차단으로 쓰지 말 것**(오탐 — 킷 `tamper-check`가 경고성인 이유. 실질 판정은 `/done`의 `/code-review`)
> - **고위험 게이트**(2026-09-09 현재: `셀프승인` 라벨이 **파이프라인 생성 전에** 붙어 있으면 ▶ 없이 자동 통과 · 라벨 없는 MR 과 **되돌리기 어려운 경로**(`CLAUDE.md`·`.gitlab-ci.yml`·`.claude/**`·`.husky/**`·`.gitattributes`·`k8s/**`)·`고위험` 라벨 MR 은 `when:manual`): 입구는 **둘 — 경로 기반(`high-risk-gate`) + `고위험` 라벨 기반**이고, `CLAUDE.md`·`.claude/**`·게이트 스크립트 같은 **방어선 자체를 바꾸는 변경에도 발동**한다(경로 목록 정본 = CI의 `changes:`). 본인 통과가 표준(경고 레인) — 잡이 실행자=작성자를 판정해 **`셀프승인` 라벨 없인 exit 1**로 막는다
> - docs만 바뀐 커밋은 test 생략 / main 머지 = 검수 서버 자동 배포(+헬스체크) — ※이 두 줄은 **스택·배포 잡 활성화 후** 기준(킷 기본은 test 주석 스텁·deploy는 echo 시뮬)

> ★**사람 코드리뷰가 없는 구조에서는 CI가 유일한 자동 안전망**이다 — 외부 증거가 강하게 경고하는 지점이다(무리뷰 머지와 결함률 급증의 상관, AI 코드의 보안 결함 급증은 빌드·타입·테스트로는 안 잡힘). 그래서 위 검사·게이트 잡들은 "여유되면"이 아니라 **P1(셀프 머지를 켜기 전 필수)**다. 근거·출처: `4-reference/team-ai-collab-evidence.md`(프레임워크 홈) §2-1·§2-2·§3.

> ★**AI 리뷰 정본 = `/done` 4단계**(저장 워크플로 `/merge-review`, 없으면 `/code-review xhigh`. ⚠️`ultra` 는 **별도 과금이라 금지** — 2026-09-08 오너 결정). 개발자 구독으로 도는 범위 안이라 **추가 결제 0.** 자기선호 편향은 그 `/code-review`를 **새 서브에이전트(fresh context)**로 돌려 피한다(같은 Claude Code 구독 안이라 비용 없음). 이게 셀프 머지의 AI 안전망이다.
> 〔P2 — 선택, **별도 API 결제**〕 CI에서 MR마다 `claude -p` 자동 리뷰 잡을 추가할 수도 있으나 **"비용 신경 끄기" 원칙이면 도입하지 않는다** — 구독 `/code-review`로 충분하다.

> ⚠️ **`.gitlab-ci.yml` 변경은 push 전 `glab ci lint` 한 번** — 셸 따옴표 안의 콜론+공백(`: `)을 YAML이 매핑으로 오해해 파이프라인 전체가 조용히 FAILED되는 함정이 있다(파일럿 실증).

**▶ `/setup-gitlab` 실행** — 라벨·보드 열(진행중·검수요청, `고위험` 포함)·main 보호·Pipelines must succeed·멤버 권한을 glab으로 **한 번에** 설정합니다(손으로 클릭하던 반복 작업을 대체 — 하나 빠지면 카드가 조용히 실패하니 스킬로 확실하게).
**⚠️ 비개발자 권한 — 세 가지만 기억:**
- **권한**: 기획/디자이너 = `Maintainer`(이슈·댓글 + `docs/` 직접 편집·커밋). 이 팀은 비개발자가 문서를 웹에서 직접 올리고 고친다(길 A — [GitLab 가이드](AI_Working_Framework_Guide_GitLab.md) §1·§7).
- **필수 안전장치**: main 보호(MR 전용) + Pipelines must succeed. 이러면 비개발자의 문서 변경도 MR로 흐르고(본인이 셀프 머지 — Maintainer라 가능), 실수로 코드를 건드려도 CI·고위험 게이트가 잡는다.
- **CE 한계와 백스톱**: 사내 GitLab(CE)은 "docs만 허용" 같은 경로별 보호가 안 된다(유료 기능) → "비개발자는 docs만"은 **가이드 명시 + CI 사후 감지 잡 planner-guard**(`PLANNER_EMAILS` 등록으로 발효)로 백스톱한다.

> ⚠️**고위험 카드 = 경고 레인 — 정의·절차의 정본은 킷 `CLAUDE.md` '머지 등급' 절이다.** 요약 3줄:
> - 고위험(인증·결제·DB 마이그레이션·shared 승격·핫스팟)은 CI 통과에 더해 **AI 경고 리뷰 + 증적 3종**(①리뷰 경고의 채팅 보고 ②본인 diff 확인 ③카드 "셀프 승인" 댓글)을 남기고 **본인이 게이트를 실행·머지**한다 — 증적 없이 조용히 머지 = 무승인.
> - **머지 등급의 정의·절차 정본 = `CLAUDE.md` '머지 등급' 절**(여기 요약은 정본이 바뀔 때마다 갈린다 — 2026-09-09 실측).
> - **동료 승인은 선택** — 민감하다 싶으면 요청하되 없다고 멈추지 않는다(필수 동료 승인은 소규모 팀 병목이라는 실측이 근거 — 상세는 CLAUDE.md). "경고 무시" 건수는 `/metrics`가 센다 — 늘면 레인을 재검토한다.
> - 무료 티어라 기계 차단 대신 **`고위험` 라벨 + `/done` 게이트 흐름**의 팀 규율로 운영하고, 대다수 일반 카드는 셀프 머지 그대로다. 도입 근거 = `4-reference/team-ai-collab-evidence.md`(프레임워크 홈) §2-1.

> ⚠️ **사내 러너 확인:** 공용 러너 큐가 밀리면 auto-merge가 전부 러너 대기에 묶인다. CI 한 바퀴가 5분을 넘으면 프로젝트 전용 러너를 요청하라 — 이 방식 전체가 "CI가 빨라야" 굴러간다.

**완료 기준:** 아무 브랜치나 MR 생성 → CI가 돌고 → 머지하면 검수 서버에 반영되는 것을 눈으로 확인. (검수 서버 인프라가 아직 미확정이면 → **deploy 잡 로그의 시뮬 echo 확인으로 대체 판정**하고, 실배포 확인은 인프라 확정 후로 미룬다 — Day 3 표의 `<검수서버URL>` 비고 참조)

**작성 원칙:**
- **짧게** — 루트 CLAUDE.md의 **기계 상한 = 200줄 · 줄당 300자**(`scripts/check-density.sh`가 검사, CI `density-check`). 실제 방어선은 줄 수보다 **가지치기 규율**(3절 회고의 가지치기 참조). 파일당 한 주제. **절차(단계 있는 워크플로)는 여기 말고 스킬로**(Day 5) — 공식 가이드: "CLAUDE.md의 한 절이 절차로 자라면 스킬로 옮겨라".
- **중복 없이** — 루트 = 전역 사실·경계·금지, rules = 그 영역의 사실. 두 곳에 쓰면 한쪽만 고쳐져 모순이 생긴다.
- 다른 AI 도구(Cursor 등) 혼용 팀이면: 내용을 `AGENTS.md`(업계 표준)에 두고 **CLAUDE.md 첫 줄에 `@AGENTS.md` 임포트 한 줄** — 방향 주의(반대로 하면 Claude가 못 읽는다). Windows라 심볼릭 링크는 못 쓴다.
- 운영 규칙 2개가 킷 CLAUDE.md 세션 규칙에 **있는지 확인**(새로 쓰는 게 아니다): **"세션은 항상 repo 루트에서"** · **"이슈 하나 = 세션 하나"**(시작은 그냥 `claude`, `-n` 이름표는 이어갈 이슈만 선택).

> 💻 **예시**: 이 Day는 명령 하나가 아니라 **아래 체크리스트**(킷 스크립트 연결·검증). `/scaffold`가 상당수 처리했음.

> ⚠️ **git 훅은 clone만으로 설치되지 않는다.** `.git/hooks`는 버전 관리 밖이다 — repo에 스크립트를 커밋해도 팀원에게 자동 적용되지 않는다. **husky(npm install 때 git 훅을 전원에게 깔아주는 도구)를 쓰고 `package.json`에 `"prepare": "husky"`를 넣어라** — 그러면 `npm install` 순간 전원에게 훅이 깔린다. 이걸 빼먹으면 "훅이 있다고 믿는데 아무한테도 없는" 상태가 된다.

> ⚠️ **Windows 랩탑 주의 4가지:** ①Windows엔 네이티브 샌드박스가 없다 — **권한 규칙(Day 3의 settings.json)이 로컬의 유일한 강제층**이니 반드시 커밋. ②`bypassPermissions`/`--dangerously-skip-permissions`(및 자동승인 auto 모드)는 팀에 절대 안내하지 말 것 — ★**자동승인 세션에선 push 훅의 확인창(ask)을 Claude Code 실행기가 소리 없이 통과시킨다**(파일럿 실측). 그래서 공통 영역 통제의 진짜 백스톱은 훅이 아니라 **①사전 채팅 공지 규율 ②CI의 고위험 차단 게이트(정본 = 킷 CI `high-risk-gate` — 수동 통과 전 머지 불가)**다. 훅은 대화형 세션의 리마인더로만 신뢰하라. ③전원 Claude Code 최신 버전 사용(구버전엔 Windows 워크트리 삭제 시 링크 대상 파일이 지워지는 버그). ④**전원 `CLAUDE_CODE_GIT_BASH_PATH` 환경변수 설정**(절차 = ONBOARDING 첫날 셋업, 미설정 증상 = Day 5 트러블슈팅 표) — 강제 장치가 전부 bash 스크립트라 이게 빠지면 조용히 안전장치 없이 도는 셈.

> ⚠️ **"이미 킷에 있다"와 "지금 만든다"를 구분하라.** **킷 훅 목록 정본 = `.claude/settings.json` 의 `hooks` 절**(2026-09-09 현재 `check-push.sh`·`session-guard.sh`·`ensure-user-settings.cjs` 셋 + security-guidance 플러그인 — 여기에 열거하면 갈린다)뿐이다. 나머지 — **husky(+`"prepare":"husky"`)·shared 공개 API 스냅샷 테스트·lock 충돌 안전판(아래 4번)·Edit/Write 모듈 가드 훅**은 **`package.json`이 생긴 뒤(=Day 1 `/scaffold` 후)에야** 만들 수 있다. 그러니 Day 4는 "확인만"이 아니라 이 넷은 **실제로 새로 만든다.**
> ⚠️ **check-push의 감지는 "파일 경로" 기준이다(테이블 이름 아님)** — 이 프로젝트의 폴더 구조가 킷과 다를 때만(예: `packages/shared/`) 스크립트의 경로 패턴을 실제 구조에 맞게 고친다. 테이블명을 채워 넣는 치환 단계는 없다.

**확인 체크리스트 — 강제 장치 6종.** 생성 주체는 한 문장으로: **1~2·6은 킷 제공(확인만), 3~5는 `/scaffold`가 생성 시도하나 package.json 시점 문제로 누락될 수 있다 — Day 4는 실물 검증이고, 빠진 건 AI에게 "N번 만들어줘"라고 하면 그 자리에서 만든다**:
1. [ ] `check-push.sh`(공통 영역 push 경고) — **Claude Code `PreToolUse` 훅 전용**이다. git 훅(husky pre-push)에 그대로 붙이면 stdin 형식이 달라 **경고 한 번 없이 무음 통과**한다(실측 경위 = `_reference/push-guard.md`). git 쪽 백스톱까지 원하면 AI에게 경로 판정 래퍼를 만들게 하라 — 안 만들면 이 항목은 Claude Code 세션 전용 리마인더고 백스톱은 CI 게이트다.
2. [ ] settings.json 훅 배선(Claude Code가 Bash `git push` 실행 전 위 스크립트 호출) — 킷 제공, 커밋돼 있는지만
3. [ ] shared 공개 API **스냅샷 테스트** — export 이름 + **시그니처 해시**까지(이름만 기록하면 파괴적 변경이 통과 — 드라이런 실측 갭)
4. [ ] lock 충돌 안전판: `.gitattributes`에 `package-lock.json merge=binary` **+ `*.sh text eol=lf`**(줄바꿈이 CRLF 로 들어가면 게이트 `.sh` 가 조용히 안 돈다) — ⚠️자동 머지 드라이버 금지(lock 자동 재생성은 **한쪽 의존성을 조용히 누락**시킨다, 2026-07-27 실측). 시끄러운 충돌로 강제하고 수동 해결한다(절차 정본 = CLAUDE.md '금지' 절)
5. [ ] ~~PreToolUse 훅(남의 모듈 편집 시점 경고)~~ — **만들지 않는다**(2026-09-01 결정: 경계 판정 정본은 CI `boundaries` 잡이다. 훅으로 이중화하면 오탐이 정상 작업을 막는다)
6. [ ] security-guidance 플러그인 활성화(settings.json `enabledPlugins`)

**완료 기준:** shared/ 파일을 일부러 고쳐 **Claude Code 세션 안에서** push → 확인 창(ask)이 뜨는 걸 직접 본다(터미널에서 맨손 `git push`로는 안 뜬다 — 이 훅은 Claude Code 전용이다. 래퍼를 만들었다면 맨손 push에서도 경고가 뜨는지 함께 본다). 스냅샷 테스트에서 export 하나를 지워보고 CI가 빨간불 되는 것도.

> 〔P2 — 여유 되면 첫 주에〕 **Stop 훅 자가검증:** "완료" 선언 전에 검증(배포 헬스체크·테스트)이 통과할 때까지 턴 종료 자체를 차단하는 공식 훅 — "검수요청 전 자가 확인" 규율을 기계로 승격한다. (**시크릿 스캔·변조 감지 등 킷 CI 잡은 Day 2 P1 필수** — 무료다(잡 목록 정본 = `.gitlab-ci.yml`). **AI 리뷰 CI 잡은 별도 API 결제**라 P2 선택이고, 비용 없이는 개발자 구독 `/code-review`가 그 역할을 한다.)

### Day 5 — 시드·리셋·ship + 파일럿 〔P1 — 레일 1회전 없이는 팀 착수 금지(§0 철칙)〕

> 🎯 **이 Day: 시드 데이터 + 예행연습(파일럿).** 공통 개발자가 직접 카드 하나를 등록→개발→배포까지 굴려보며 **레일이 진짜 도는지** 눈으로 확인해요. 여기서 막히면 고치고, **막힘없이 돌기 전엔 다음(팀 착수)으로 안 갑니다.**
>
> 💻 **예시**: `/card 푸터에 배포시각 표시` → `/dev 12` → `/done 12` → 배포 화면 확인 → `/metrics` (첫 측정)

**확인 체크리스트 — 시드·리셋** (`/scaffold`가 생성, `/done`·`/todo` 스킬이 감싸 실행 — 별도로 만들 것 없음. ~~ship 스크립트~~는 폐기: `/done`이 그 역할):
1. [ ] 모듈별 `seed.ts`(멱등 upsert — 몇 번 돌려도 결과 동일), migrate 서비스가 마이그레이션 후 실행
2. [ ] `scripts/reset-review-server.sh`(검수 서버 DB 초기화, 확인 프롬프트 포함)
3. [ ] `/done`이 이 스택 값으로 실제 도는지(최신 main 반영→테스트→push→MR·머지→검수요청 전환+멘션 — Day 5 레일 1회전이 곧 이 확인)

**Day 5 완료 기준 = 레일(파이프라인) 1회전.** 공통 개발자가 직접: 카드 등록 → **파이프라인만 태우는 사소한 변경**(예: 푸터 문구 한 줄 — 본보기 없이 가능한 것) → `/done` → 자동 배포 확인 → 검수요청 카드에 멘션 도착 확인. 여기선 **레일(CI·셀프 머지·자동 배포·검수요청)이 도는지**만 본다. **진짜 기능 개발 드라이런(본보기 + 첫 팔로워)은 Day 6이고, 팀 착수 최종 관문도 거기다.** (만든 것과 돌아가는 것은 다르다 — 골격도 검수 대상이다.)

> ⚠️파일럿에 **의도적 반려 1회 포함**: 일부러 결함 하나를 반려시켜 "검수 반려 → 카드 진행중 복귀 → 재작업(/fix) → 재검수 → Close" 한 바퀴를 직접 돌려 두라(골격 주간엔 공통 개발자 혼자 — **팀 합류 후 온보딩 파일럿에서 팀도 같은 한 바퀴를 연습**한다). 실전 첫 반려 때 즉석 규칙 발명을 시키지 마라.

> ⚠️파일럿에서 **특히 지켜볼 것** — 설계 검증(시뮬)이 구조상 확인하지 못해 실물에서만 보이는 영역들이다. 여기서 나는 마찰은 카드로 등록:
> ①CI 파이프라인·**auto-merge 실동작** (러너 속도 포함) ②**check-push 훅 실발화**(Day 4 완료 기준의 확인 창 — 1회) ③`/code-review`·`/security-review` 실호출 품질 ④기획자의 **실제 웹 편집** 경로(커밋 번호 없는 docs 커밋 처리 포함) ⑤**서로 다른 PC 두 명이 같은 파일**을 건드렸을 때의 머지 충돌 해소 ⑥husky pre-push(래퍼를 만들었을 때만 — Day 4 ①)·스냅샷 테스트 동작 ⑦glab CLI 전반(스킬의 자동 조회 줄 포함). (④⑤는 팀이 있어야 실제로 확인된다 — 팀 합류 후 확인 항목으로 열어둔다)
>
> 🔧 **레일이 안 돌 때 (증상→원인→처치):**
>
> | 증상 | 흔한 원인 | 처치 |
> | --- | --- | --- |
> | CI가 아예 안 시작 | 러너 없음/미등록, `.gitlab-ci.yml` 문법 | 프로젝트 러너 확인 · `glab ci lint` |
> | auto-merge가 안 걸림 | "Pipelines must succeed" 미설정, 파이프라인 미완 | Day 2 `/setup-gitlab` 재확인 · CI 초록 대기 |
> | 머지됐는데 배포 noop | deploy 잡 조건·검수서버 접속·헬스체크 실패 | deploy 잡 로그 · `/api/health` 200 확인 |
> | glab이 403/권한 오류 | 토큰 스코프·멤버 권한 부족 | `glab auth status` · 멤버 권한(Developer+) 확인 |
> | check-push 확인 창이 안 뜸 | `CLAUDE_CODE_GIT_BASH_PATH` 미설정 · repo 루트가 아닌 폴더에서 세션 시작 · 자동승인(auto/bypass) 세션 · **맨손 터미널 push**(이 훅은 Claude Code 전용) | 환경변수 설정 · repo 루트에서 재시작 · 일반 모드로 · git 훅에서도 필요하면 래퍼(Day 4 ①) |
> | husky로 깐 git 훅이 안 돎 | husky 미설치·`"prepare": "husky"` 누락 | `npm install` 재실행 |

> ⚠️**파일럿은 체감이 아니라 실측으로 판정한다.** 개발자들은 AI로 느려지면서도 빨라졌다고 믿는다는 실험 결과가 있다(체감은 반대로도 틀린다). 지표 4종(리드타임·결함률·리버트·반려 사유)을 **첫날부터** 본다 — **집계 방법론의 정본 = `/metrics` 스킬**(주 1회 실행).
> - ⚠️ **self-hosted 무료(CE)에는 DORA·리드타임 대시보드가 없다**(Premium/Ultimate 전용) — 그래서 `/metrics`가 GitLab 데이터에서 직접 뽑는다.
> - **임계값(무엇이 나쁜가) 예시** — 팀에 맞게 조정하되 숫자로 정해둬라: 리드타임 중앙값이 주 단위로 계속 늘면 경보 / 반려율 30% 초과면 카드 품질(수용 기준) 문제 / 리버트가 주 2회 넘으면 CI 게이트 보강 / 배포 후 버그 카드가 신규 기능 카드 수를 넘으면 속도를 늦춘다. **"스킬 사용률" 같은 산출 지표를 목표로 걸지 마라** — 게이밍된다(실사례 있음).
>
> 이 실측이 "셀프 머지 + 고위험 경고 레인 + 두꺼운 CI"가 실제로 안전한지를 증명하거나 반증한다 — 반증되면(예: 결함률이 오르면) 동료 승인을 다시 필수로 돌리거나 CI 게이트를 더 조인다.

### Day 6~ — 본보기 모듈 + 생성기 + 스킬 체계 〔P1, 팀 착수 전 필수〕

> 🎯 **이 Day: 진짜 기능 하나를 "본보기"로 끝까지 완성.** 다른 개발자들은 이걸 **베껴서** 일해요. 두 번째 모듈을 **다른 사람이 본보기만 보고** 만들 수 있으면 → 팀 착수 준비 끝. (팀을 태우는 최종 관문이 여기.)

> 💻 **예시**: `/module board` → `/dev 13` (본보기 개발) → 모듈 간 계약 정할 땐 `/adr 게시판·회원은 …로만 연동`

1. 전원 **[ONBOARDING](ONBOARDING.md) '첫날 셋업' 그대로**(clone→설치→신뢰 수락→기동까지 — 항목·순서는 그 문서가 정본) — 각자 화면 뜨는 것까지 확인

4. **이슈 비축 확인:** 보드에 최소 개발자 수 × 3장의 카드가 있어야 시작 — AI 속도에서 카드는 금방 마른다. 기획자와 함께 **`/card <요구사항 문서경로> 분해`** — 절→카드 매핑·의존·위상순(의존 순서대로 — 먼저 만들 것부터)까지 맞춰 여러 장 초안을 만들어 확인 후 등록한다(자연어 프롬프트 대신 스킬로).

> **소개 팁 두 가지:**
> - 문서를 설명하려 하지 마라 — **시연 한 번**(카드 등록 → "이슈 #1 마무리해줘" → 자동 배포 → 검수요청 멘션 도착)이 문서 일곱 개보다 설득력 있다. 각자 읽을 문서는 **ONBOARDING(역할별 1장)**대로 역할별 하나씩만 짚어준다.

## 3. 운영 중 공통 개발자 루틴

### 🔄 요구·설계가 바뀌면 (변경·피벗 대응) — 규모별 3가지
바뀌는 건 정상입니다. **규모에 따라** 대응이 달라요:

- **① 작은 요구 변경** (문구·정책 몇 개): 기획자가 **docs 정본을 직접 고침** → 개발자가 **`/change`** 실행 → 영향받는 것(열린 카드·진행중 카드·이미 구현된 코드)을 자동으로 정리(새 카드/수정/무효 닫기). 그 diff가 곧 변경 통지.
- **② 설계 결정 하나를 뒤집음** (예: 라이브러리·구조 하나 교체): **새 ADR을 쓰고** 옛 ADR에 "대체됨(→새 번호)" 표시(옛 파일 수정 ❌ — 안 그러면 다음 세션 AI가 옛 방향으로 "복원"하는 사고). 영향 전파는 `/change`로 카드화.
- **③ 큰 피벗** (스택·모듈 경계·공통 구조가 통째로 바뀜, 이미 코드가 있음): **"재기준선" 원자 MR(쪼개지 않고 한 번에 전부 머지되는 MR) 하나로** — docs 재작성 + 없어진 것 "Removed" 표시 + 대체 ADR을 **한 번에 머지** → 보드 재설정(구 카드 일괄 `무효`, 필요한 것만 새 기준으로 재발행) → 코드 정리. 필요하면 **`/design` 재실행**(설계 갱신) → **`/scaffold`**(구조 반영).

> ⚠️ **가장 위험한 건 "반쯤 피벗"**(문서 반·코드 반). 그래서 **docs·ADR을 먼저** 원자적으로 맞추고 코드가 따라오게 합니다 — **"docs가 항상 첫 수."**

**구체 시나리오: 모듈 B만 설계를 다시 해야 할 때 (A는 잘 가는 중) — 역할별로 누가 뭘, 어떤 스킬로**

| 역할 | 하는 일 (순서대로) |
| --- | --- |
| **기획자** | 바뀐 요구를 **docs 정본에 웹으로 직접 수정** (원본이 첫 수 — 채팅으로만 말하고 끝내지 않기) |
| **공통 개발자** | ① `/change`(영향 분석 — B의 열린·진행중 카드 정리: 수정/무효/신규) ② B의 **경계·스키마까지** 바뀌면 `/design` **재실행**(⑤모듈·⑥shared만 갱신) + **대체 ADR** ③ B 카드 재발행 |
| **B 소유자** | 진행중 작업 중단 → 무효/수정된 카드 확인(멘션이 옴) → 새 카드로 `/dev` 재착수. **B 경계 안**(내부 구조·파일)은 소유자 재량 — 절차 불필요 |
| **A 소유자** | **그대로 진행** (B의 재설계가 A를 안 막는다 — 모듈은 서로 `index.ts`로만 연결). 단 **A↔B 계약(인터페이스)이 바뀔 때만**: 새 계약 ADR에서 @멘션 받고 시그니처 확인 → 호출부 수정은 B 소유자의 기계적 수정(+@멘션)을 기다린다 |
| **검수 담당** | 무효 카드 알림(멘션) 확인 — "완료였던 것"이 무효되면 재검수 대상 파악 |

> 격리가 되는 이유(구조): 모듈 = **수직 슬라이스**(화면+API+DB 통째 한 폴더) + 남의 모듈은 `index.ts`(공개 인터페이스)로만 import(내부 직접 import는 **CI 경계검사가 빨간불**) + 한 모듈 = 한 소유자(남의 모듈 수정 금지). 그래서 B 안에서 무슨 일이 나든 A가 받는 영향은 "B의 index.ts가 바뀌나"뿐이고, 그 변경은 ADR+멘션으로만 일어난다.



### 주 1회 30분 — 회고 (첫 달, 이후 2~4주 간격으로 완화)

"버릴 것 / 더할 것 / 유지할 것" 세 질문, 액션은 **1~2개만**, 액션은 말이 아니라 스킬·CI·CLAUDE.md 수정으로 반영 (지난 회고 액션이 반영됐는지 확인부터 — 이게 안 되면 회고가 죽는다).
회고의 완료 기준: 액션이 말이 아니라 diff로 남았는가(스킬·CI·CLAUDE.md 변경 커밋 또는 카드).

> ⚠️**규칙·스킬은 늘리기만 하면 죽는다.** 규칙이 많을수록 AI 준수율이 떨어지고(연구·공식 문서 확인), 안 쓰는 스킬은 방치되면 부패한다. 그래서 회고에 **가지치기**를 넣는다: ①CLAUDE.md에 규칙 1건 추가하면 **삭제/훅 전환 후보 1건**을 함께 찾는다(순증 지양) ②규칙마다 "이 줄을 지우면 실제로 실수가 나나?" — 아니면 뺀다 ③스킬 사용 빈도를 보고 **거의 안 쓰는 스킬은 죽인다**(19종 전부 생존은 드물다). 자주 위반되는 고비용 규칙은 CLAUDE.md에 더 쓰지 말고 훅/CI로 기계 강제로 옮긴다.

> 💬 **질문 = 가이드 갭 신호.** 팀원의 질문에 가이드의 절을 짚어 답하지 못하면 그건 그 사람 문제가 아니라 **가이드의 구멍**이다 — 그 자리에서 보완 카드 1장을 만든다(말로 때우면 다음 사람이 또 묻는다).

> 🔧 **킷 개선 수집·수리 필터** (개발자 AI가 구멍을 밟고 조용히 우회하는 게 기본값이 되지 않게): 수집 창구는 하나 — **`docs/friction.md` 한 줄**(막혔다/우회했다는 줄 머리 `[막힘]` 태그. `킷개선` 라벨 카드 채널은 폐지 2026-08-09 — 카드화하면 보드가 뒤덮이고, 커밋 동봉 파일이 유실 감지도 더 낫다). **«주 1회 회고» 규약은 폐기됐다 — 주체·트리거가 없어 한 번도 안 돌았다**(2026-08-12·08-31 실측: 이 파일을 건드린 커밋 71건 중 판정 표기 3건, 마지막이 08-14). 지금은 ⑴`[막힘]`을 적은 세션이 **«마찰 수거» 카드에 멘션 댓글**로 소유자에게 알리고 ⑵수리한 쪽이 **같은 커밋에서 줄을 닫으며** ⑶`/todo` 0-c 가 백스톱으로 훑는다(⑴은 2026-09-04 신설 — 그전엔 «발견은 무음, 해결만 알림»이라 오너가 **남이 고친 뒤에야** 자기 몫이 밀려 있던 걸 알았다). **수리 필터**는 그대로다: ①`[막힘]` = 즉시 수리 ②그 외 = **같은 것이 두 번 나오면** 수리(한 번은 우연, 두 번은 패턴 — shared 승격 기준과 같은 논리) ③나머지 = 기록만(킷을 매번 고치면 그게 다시 전 repo 동기 비용). 수리분은 킷 정본(ai-framework)에 먼저 반영 후 동기. **수리로 스킬 본문에 실측 예외를 보탤 땐 새 줄 500자 상한**(넘으면 하위 항목으로 쪼갠다 — 절차와 예외가 한 줄에 섞이면 절차가 흐려진다는 밀도 실측 2026-07-29. 단 **기존 실측 예외를 삭제·요약하지는 마라** — 한 번 겪어야 아는 지식은 복원 불가). 스킬당 **약 5,400자**(공식 한도는 「컴팩션 시 스킬당 5,000토큰까지만 재부착」이고, **한국어 1자 ≈ 0.93토큰** — 2026-09-07 실측: `/dev` 13,003자 = 12,072토큰)를 넘보면 함정만 보조 파일로 빼는 분리를 검토하되, **분리 후 실제 한 바퀴 태워 보조 파일을 찾아 읽는지 실증한 뒤에만**(실증 완료 2026-09-07 — 격리 프로브에서 강한 지목·약한 지목 **둘 다** 보조 파일을 `cat` 으로 읽고 그 규칙을 따랐다. n=1씩·짧은 세션·파일 2개뿐이라 «지목 강도는 상관없다»까지 단정하지는 마라). ★**바이트로 재지 마라 — 한글 1자가 3바이트라 세 배로 부푼다**(같은 날 `wc -c` 로 재서 「25KB, 기준의 두 배」라 오판했다. 결론은 우연히 맞았지만 근거가 틀렸다). 재는 법: `python3 -c "import io,sys;print(len(io.open(sys.argv[1],encoding='utf-8').read()))" <파일>`, 토큰 실측은 `claude -p --output-format json` 의 usage 합(input+cache_creation+cache_read)을 빈 프롬프트 기준선과 빼서. **줄 수 상한은 별개로 500줄**(공식·소프트) — 킷 스킬은 전부 그 아래다. ★★**넘으면 «앞 5,000토큰만 남기고 뒤가 잘린다»**(2026-09-07 공식 재확인 — 드롭이 아니라 절단). 그래서 **빼야 할 것은 «함정»이 아니라 «뒤쪽 절»이다**: 앞에서부터 세어 5,000토큰 밖으로 밀려나는 부분이 컴팩션 뒤 통째로 안 읽힌다. **보조 파일은 이 예산에 안 든다**(읽을 때만 로드) — 잘려서 안 읽히느니 포인터로 읽히는 편이 낫다. ⚠️**재부착 전체 합산 예산은 25,000토큰이고 최근 호출 순**이라, 한 세션에서 스킬을 많이 부르면 **오래된 스킬은 통째로 빠진다** — 긴 세션에서 옛 스킬 규칙을 기억할 거라 기대하지 마라.

> 🔑 **권한 프롬프트 마찰**이 올라오면: 내장 `/fewer-permission-prompts`로 허용목록 후보를 채굴 → **공통 개발자가 검토 후 킷 `settings.json`에 커밋 배포**(각자 개인 settings에 넣으면 팀 드리프트 — 권한은 커밋 배포가 원칙).

## 4. 오픈(실사용 전환) 전에 정할 것들 — 지금은 범위 밖, 그날 오면 이 목록부터

이 설계는 **검수 서버까지**를 다룬다. 실사용자가 들어오는 순간 달라지는 것들 — 오픈 결정이 나면 이 목록을 카드 묶음으로 만들어 처리한다:

- [ ] **환경 분리**: 검수 서버(매 머지 배포)와 운영 서버(안정 버전만)를 나눌지, 운영 배포는 어떤 절차로 (버전 태그? 수동 승인?)

- [ ] **장애 대응**: 죽으면 누가 어떻게 아는가(모니터링·알림), 연락 체계, 롤백 절차 (Framework STEP 9~10 산출물이 이 자리)
- [ ] **운영 데이터 등장 후의 스키마 규칙 격상**: 실데이터가 쌓이면 파괴적 변경의 대가가 커진다 — 확장→이전→축소 규칙이 "권장"에서 "필수"로
- [ ] 실사용자 계정·권한 체계 (검수용 데모 계정과 분리)

## 5. 공통 개발자가 빠지면 (부재 대비)

- 공통 개발자 권한(GitLab Maintainer)을 **한 명 더** 부여해 둔다 — 설정 변경·리셋 스크립트 실행 대리
- 사건 대응 절차(위 표)가 이 문서에 있으므로, 대리자는 이 문서대로 하면 된다
- 골격 관련 지식이 공통 개발자 머리에만 있으면 안 된다 — 골격의 구조·이유는 루트 CLAUDE.md와 이 가이드에 다 적혀 있어야 한다 (적히지 않은 결정이 생기면 그때그때 추가)

### 팀원 이탈 (개발자·기획자 — 통보 당일 시작)

- **개발자가 떠나면**: ①WIP(하다 만 작업)를 브랜치 push + 각 카드에 상태 한 줄 댓글("어디까지 됐고 다음은 무엇") ②모듈 이관 = `/assign-module {모듈} {새 소유자}` ③**떠나는 사람 앞 열린 카드를 일괄 재배정**(공통 개발자) — 당장 이을 사람 없으면 전이표의 `진행중→대기` 되돌림으로.
- **기획자가 떠나면**: ①**요구 결정권자 1인을 승계 지정**부터 — 요구 판단 공백 = 개발 전체가 멈춘다 ②그 사람 앞 검수 배정 카드 재조정 ③`<기획자아이디>` 멘션 대상 갱신(CLAUDE.md만 — 스킬·rules는 실행 시점에 CLAUDE.md를 읽는다).
- 공통: 계정은 이탈일에 비활성화(토큰 포함), 마지막 주에 후임과 카드 하나를 같이 처리해 흐름 인수.
