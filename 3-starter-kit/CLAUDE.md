## 세션 규칙
- **사용자에게는 존댓말로 답한다** — 이 파일과 스킬 문서는 *AI에게 내리는 지시문*이라 하다체(`따른다`·`하라`·`금지`)로 쓰여 있다. **그 문체를 사용자 응답에 그대로 옮기지 마라**(규칙 문서를 많이 읽은 세션일수록 끌려간다 — 2026-07-30 실측). 규칙 문서의 문체 ≠ 사람에게 하는 말
- **세션은 항상 repo 루트에서 켠다** (팀 권한·훅은 켠 폴더의 것만 적용됨)
- **이슈 하나 = 세션 하나** (한 세션에서 여러 이슈 이어가기 금지 — 긴 세션은 규칙 준수율을 떨어뜨린다). 시작은 그냥 `claude`면 충분. (선택) 다음 날 이어갈 이슈면 `claude -n issue-{번호}`로 이름 붙여 두면 `claude --resume issue-{번호}` 복귀가 쉽다
- **동시에 두 이슈를 다루면 이슈별 `git worktree`(또는 별도 클론)** — 같은 클론에 세션 둘 금지
  (한쪽의 checkout이 다른 쪽 커밋을 남의 브랜치에 얹는다 — 실사고 사례 있음). 각 워크트리는 **자기 포트·자기 로컬 DB**를 쓴다(`CLAUDE.local.md`에 내 포트 기록) — 안 그러면 두 세션이 같은 포트·DB를 놓고 무음으로 덮어쓴다
  → **레시피·Windows 주의·트리 신뢰 확인**은 `_reference/worktree.md`
- **CLAUDE.md ↔ CLAUDE.local.md — 네가 기록할 위치의 판단 기준**: 팀 규칙·절차 = **이 파일**(공통 영역 — 함부로 수정 금지, 변경은 사전 채팅 공지+카드로) / 개인 로컬 값(내 포트·로컬 DB명·개인 메모) = **`CLAUDE.local.md`**(커밋 금지 — .gitignore). **반대로 넣지 마라**: local에 적은 팀 규칙은 남에게 적용되지 않고, 이 파일에 적은 개인 값은 전원의 AI를 오염시킨다. 개인 값을 기록해야 하는데 `CLAUDE.local.md`가 없으면 그 자리에서 만들어라(양식 = `/start` 1-1)
- 세션 시작·이슈 마무리 후·사용자가 다음 작업을 물으면 `/todo` 를 실행해 번호 선택지로 제시하라
- **네가 띄운 로컬 서버·백그라운드 프로세스는 작업 종료 전 반드시 종료하라** — 고아 프로세스가 다음 사람의 포트·폴더를 잠근다

## 머지 등급 — 대부분 셀프, 고위험만 동료 1명 확인
- **기본 = 셀프 머지**: CI(빌드·타입·테스트·경계검사 + 보안·변조 스캔)가 초록불이면 사람 승인 없이 머지한다. 이게 표준 흐름이다 — 전담 승인자는 없다.
- **★고위험 카드 = Ask 레인**: 아래에 해당하면 CI 통과에 더해 **아무 동료 개발자 1명의 MR 승인** 후 머지(전담 리뷰어가 아니라, 손 빈 동료 아무나 1명). 자기 코드를 자기가 승인하지 않는다.
  - 인증·인가·세션·비밀값 취급 / 결제·과금성 로직 / **DB 마이그레이션** / **shared 승격**(2개 모듈+가 쓰는 코드) / 라우팅·설정·lockfile 등 핫스팟 파일
  - 고위험이면 카드에 `고위험` 라벨을 달아 표시한다(/card·/change가 유형 보고 자동 판단·제안). 애매하면 고위험으로 취급.
  - **승인자는 개발자끼리 서로** — 공통 개발자는 승인자가 아니다(개발자가 1명뿐일 때만 예외). 몰리면 그가 전담 리뷰어가 되어 이 규칙이 막으려던 구조가 생긴다(2026-08-06 실측).
  - **★셀프 승인도 인정한다 — 단 증적 3종을 남길 때만**(동료 승인 불가: 혼자 골격 작업·전원 부재·긴급). 셋이 다 남아야 셀프 승인 — **조용히 머지 = 무승인**:
    - ①fresh-context AI 리뷰(`/code-review`, 새 입력 표면이면 `/security-review`도) ②본인이 diff 직접 확인 ③카드 댓글에 "셀프 승인" + 사유 + 리뷰 결과 + 확인한 diff 범위.
    - AI 리뷰를 같은 세션(구현한 컨텍스트)에서 돌렸으면 그 사실도 적는다(편향 가능성이 증적의 일부).
  - **동료가 있으면 동료 승인이 우선** — 셀프는 폴백이지 기본값이 아니다. 셀프 승인이 반복되면 그 자체가 신호이니 `/metrics` 주간 점검에서 세어 본다.
  - 근거: 전면 무리뷰의 성공 선례가 외부에 없고(Anthropic·Google도 사람 리뷰층 유지), 고위험 경로만은 사람 확인을 두라는 게 증거의 일치된 권고다. 나머지 대다수 카드의 속도는 그대로 지킨다.

| 전이 | 주체 | 시점·조건 |

| 대기 → 진행중 | 개발자(AI) | 카드 착수 시 |
| 진행중 → 검수요청 | 개발자(AI, /done) | **머지 확인 후.** auto-merge 대기로 세션을 끝내야 하면 카드에 "MR 준비완료(!번호)"만 남기고, 다음 /todo 때 머지 확인 후 전환 |
| 검수요청 → 완료 | **사람만** — 카드의 "검수" 필드에 지정된 사람(비면 작성자). 전담 검수자는 없다(개발자든 비개발자든) | 화면 확인 후 — AI는 절대 카드를 닫지 않는다 |

| <모듈b> | (팀 태울 때 기입) |

> 이 표가 비어 있으면 /card 배정·/start 진단이 성립하지 않는다 — **기입·갱신은 공통 개발자 몫**(팀 합류·이관 때마다). **행 수 = `/design`이 정한 모듈 수만큼**(위 4행은 예시일 뿐 4개로 고정 아님). 기능 영역이 개발자보다 많으면 관련 영역을 한 모듈로 묶거나 한 사람이 여러 모듈을 소유한다.

- `src/modules/{x}` 는 소유자만 수정한다. 다른 모듈은 그 모듈의 `index.ts` 만 import. **DB도 같다 — 남의 모듈 소유 테이블 직접 쿼리 금지**(경계검사는 import만 본다): 데이터가 필요하면 그 모듈 index의 공개 함수로, 없으면 인터페이스 카드
- 공통 영역(`src/shared/`, 공용 테이블, 루트 CLAUDE.md, package.json 의존성, **flags 파일**) 변경은 **코드에 손대기 전에**
  변경 요약을 팀 채팅(<팀채팅주소>)에 공지한다 — 허락이 아니라 알림.
  ★**push 게이트 = 역할 분리**(경위·4구멍 실측은 `_reference/push-guard.md`): 일반 push=settings allow · force=settings deny · 공통 영역 감지=훅. **훅은 ask만 낸다**(allow를 내면 임의 명령까지 통과). auto/bypass 세션 훅은 미보장 — 최후 보루로 믿지 마라.
- **★공통 영역이 섞인 push는 어느 경로로든(킷 동기·규칙 수정·카드 #1 직push 포함) push 전에 포함 내용을 텍스트로 알리고 확인받는다** — /done 5단계만이 아닌 전역 규칙(무확인 push 2회 실측).
- 남의 모듈 수정 금지. 유일한 예외: shared 변경에 따른 기계적 호출부 수정 (해당 소유자 @멘션 필수)
- **모듈 간 연동**: 필요한 기능이 상대 모듈의 `index.ts`에 없으면 — 그 모듈을 직접 고치지 말고,
  **`/card` 로 소유자 앞 카드 등록을 제안**하라 (원하는 함수 시그니처를 카드에 명시).
  **두 모듈에 걸친 기능은 인터페이스(계약)와 되돌리기 어려운 결정(ADR)을 병렬 착수 *전에* 확정한다** — 파일이 안 겹쳐도 서로 다른 가정으로 만들면 합칠 때 깨진다(암묵적 결정 충돌). 계약이 정해지기 전에는 양쪽 다 착수하지 마라. **계약·shared 설계에서 이견이 좁혀지지 않으면 공통 개발자가 최종 결정한다(타이브레이커)** — 결정은 ADR로
- shared 승격 기준: **2개 이상 모듈이 실제로 쓰거나, 둘째 사용처 카드가 확정됐을 때.** 하나뿐이면 자기 모듈에 둔다 (첫 승격은 "둘째 필요가 생긴 순간"에 일어난다 — 그 전에 미리 만들지 마라)

## 작업 절차 (스킬로만)
- **일은 스킬로 진행한다.** 상태를 바꾸는 작업(코드·카드·머지·문서·스키마)은 반드시 스킬로 진입한다.
  사용자가 자연어로 시키면 — 조회·안내·등록·검사(`/start` `/todo` `/log` `/card` `/inspect`)는 네가 그 스킬을 **즉시 실행**하고,
  실행 절차(`/dev` `/fix` `/done` `/module` `/docs` `/change` `/ui` `/metrics`, 공통 개발자의 `/design` `/scaffold` `/setup-gitlab` `/assign-module` 포함)는 해당 명령 입력을 안내하라. (`/adr`은 /dev·/change 절차 중엔 네가 이어 실행해도 된다)
  **"알아서 다 해줘"·"맡길게"처럼 전권을 위임받아도 이 원칙은 그대로다** — 준비(조사·계획·카드 정리)까지만 하고 실행 절차 앞에서 멈춰 명령 입력을 안내하라. 위임 발언은 게이트 통과가 아니다(구현·머지를 시작할 권한은 스킬 명령과 그 게이트만 준다).
  사용자가 **뭘 해야 할지 모르거나 처음이면** `/start` 를 실행해 진단하고 다음 한 걸음만 안내하라.
- **★남기기 전 미리보기 — 전 스킬 공통**: GitLab·repo에 남는 산출물(카드·댓글·멘션·라벨·MR·auto-merge·머지·docs 배치·ADR·시안)은 **만들기 직전 요약(3~5줄) 보여주고 OK 후 실행**. 목적은 통제가 아니라 **가시성**(확인하는 순간마다 사람이 프로젝트 흐름을 익힌다).
  - 동종 여러 개(분해 카드 등)는 배치 1회 확인 — 단 **승인된 계획에 명시된 산출물까지만**(계획 밖이 생기면 다시 확인).
  - 선택지 게이트가 등록 승인을 겸하면 핵심 필드(제목·수용 기준·라벨·담당)를 접지 말고 펼쳐 보여준다.
  - 해당 없음: 조회·읽기·테스트, 작업 브랜치 커밋·push(/dev·/fix 계획 승인에 포함된 실행).
  - 미리보기에서 산출물 **방향이 바뀌는 수정**이 나오면 요지를 관련 카드에 댓글 한 줄(소소한 문구 손질 제외).
- **전제조건 먼저 — 스킬은 빈틈을 메우게 안내한다.** 필요한 게 없거나 정의 안 됐으면(소유표 공란·설계 미완·라벨/플레이스홀더 미설정) **감으로 진행하거나 조용히 실패하지 마라**: ①무엇이 빠졌는지 말하고 ②채우는 스킬·담당자를 `▶ 다음`으로 짚고 ③필요하면 공통 개발자에게 통지 ④채워지면 원래 작업으로 잇는다.
  - 예: `/card`인데 모듈 소유자가 소유표에 없으면 → "공통 개발자가 `/assign-module <모듈> <사람>` 먼저" 안내 + 통지.
- **다음 명령 안내 (항상)**: 작업 관련 응답의 **마지막 줄은 반드시 `▶ 다음: /명령 …`** 로 끝내라 —
  사용자는 명령을 외우지 않는다. 다음이 사용자 판단이면 선택지를 명령 형태로 2~3개 제시하고,
  다음이 명령이 아니면(예: 화면 확인) 그 행동을 적되 그다음 명령까지 이어 적어라 (`▶ 다음: 화면 확인 → 이상 없으면 /todo`)
  **스킬 절차를 임의로 흉내 내 일부만 수행하지 마라** — 절차 생략이 사고의 시작이다.
  자유 대화는 질문·코드 탐색·장애 진단용이다.
- **📍 위치 배너 (다단계 스킬 공통)**: 게이트 정지·재개(다음 /todo에서 이어받기 포함) 응답의 **첫 줄에 `📍 /스킬 N단계({상태})`** 를 붙여라 — 게이트를 오가는 동안 사용자가 자기 위치를 잃는다(실측 피드백 2026-07-24).
- **★git pull·merge 충돌은 어디서 나든 종류별 규칙대로**(/dev·/fix·/done pull이든 수동이든 — /done 전용 아니다). **임의로 한쪽만 버리지 마라.**
  - 일반 코드: 양쪽 의도를 살려 해결 후 사용자 확인.
  - package-lock은 package.json만 해결 후 재생성 / 선언형 스키마는 union+검증 / 마이그레이션은 최신 뒤로 재정렬 (상세: '스키마·데이터'·'금지' 절).
  - DB 리셋 요구 = 되돌리기 어려운 파괴적 작업 → **사람이 실행**(AI 대행 금지, 일부 도구는 AI 실행 차단).
- 기능 개발: `/dev {이슈번호}` / 작은 수정: `/fix {이슈번호}` / 새 모듈: `/module {이름}`
- 검수 반려·카드 댓글 반영: `/fix {이슈번호}` — 스킬이 반려 사유 댓글까지 읽는다 (규모가 크면 /dev)
- 카드가 없는 일을 요청받으면: **먼저 `/card {한 줄}` 로 카드를 만든다** — 카드 없는 코드 변경 금지 (요구사항 변경·삭제는 /change)
- **★스킬·규칙대로 못 하고 우회했다면 그 자리에서 `/card {한 줄}` + `킷개선` 라벨** — 우회를 조용히 넘기지 마라(공통 개발자가 주 1회 모아 킷으로 올린다). '막힌 건 아닌데 매끄럽지 않았다'는 카드 대신 **`docs/friction.md`에 한 줄 append**(`YYYY-MM-DD /스킬 — 한 줄`, 진행 중 커밋에 동봉 — 별도 절차 없음)
- 이슈 마무리: **`/done {이슈번호}` 로만** 한다 — 네가 임의로 머지 절차를 시작하지 마라
- 받은 기획·디자인 문서 정리: `/docs {파일경로}` (압축·폴더 = 수신함에 풀고 확인 후 정본 배치) / **기획자가 웹으로 이미 올렸으면 인자 없이 `/docs`**(배치 검토만) — 어느 쪽이든 STEP 문서면 **digest·`_STEP_INDEX` 갱신까지가 /docs의 일**
- **커밋 메시지 첫 줄은 `#카드번호 무엇을 했는지`** — git 이력이 카드와 연결되어 "누가 언제 무엇을 왜"가 추적된다 (이력 조회는 `/log`). 별도 변경 로그 파일은 만들지 않는다 — git이 그 로그다. (docs 변경 커밋도 관련 카드가 있으면 번호를 단다 — **기획자는 docs를 웹에서 직접 편집·커밋**한다[길 A], 코드에 영향이 있으면 카드로 남긴다. 예외: repo 최초 구축은 카드 #1을 먼저 만들고 그 번호로)
- 구현은 **본보기 모듈(`src/modules/<본보기모듈>`)을 먼저 읽고** 그 패턴을 따른다 — 따르는 것은 **관례**(파일 위치·index 노출·테스트 형태·플래그)다. **업무 성격이 달라 구조가 안 맞으면 의식적으로 벗어나되 이유를 카드 댓글(구조 결정이면 ADR)로 남긴다 — 무언의 발산 금지.** 본보기가 아직 없거나 `<본보기모듈>`이 미치환이면 **추측하지 말고 공백으로 보고**한다

## 스키마·데이터 (DB·마이그레이션 도구가 있는 스택만 — 없으면 킷 설치 때 이 절·rules/migrations.md·/done의 '마이그레이션 적용' 단계를 제거하고 남는 단계 번호를 당겨라)
- 마이그레이션 파일명 = 날짜시각(`YYYYMMDD_HHMMSS_설명`). main 에 머지된 파일은 불변
- 되돌릴 때는 down 이 아니라 "되돌리는 내용의 새 마이그레이션"을 추가한다
- 스키마를 바꾸는 MR에는 해당 모듈 시드(멱등) 갱신을 같이 포함한다
- **★마이그레이션 = 모듈 소유로 못 막는 전역 직렬 자산**: 만들 카드는 착수 전 팀 채팅 한 줄 공지, 머지는 생성 순서대로 직렬. 내 브랜치가 뒤처진 새 마이그레이션이 main에 들어왔으면 내 것을 최신 뒤로 재생성. (왜·벤더 경고: `_reference/schema-conflicts.md`)
- **★선언형 스키마 파일**(Prisma `schema.prisma`·Drizzle 등 한 파일에 여러 모듈)**은 package-lock처럼 동시 편집 충돌 자산**: 충돌 시 양쪽 정의 합친 뒤 도구 검증(`prisma validate`), 잦으면 모듈별 파일 분리. 충돌 뒤 리셋 요구 = 파괴적 작업이라 **사람이 실행**(AI 대행 금지). (실측·상세: `_reference/schema-conflicts.md`)

## 구현이 docs 스펙과 달라질 때
- 같은 MR에 docs 수정 동봉 + 카드 댓글에 "스펙과 달라진 점·이유" + @<기획자아이디> 멘션
- 문서와 구현이 말없이 어긋난 채 머지 금지. 애매하면 머지 전에 사용자에게 물어라

## 변경·삭제
- **docs 정본은 "현재 상태"만 담는다** — 요구가 바뀌면 새 파일을 만들지 말고 `docs/03_Requirement/`의 해당 파일을 *고친다*(변경 경위·이력은 카드와 git이 안다). 문서를 쌓지 않는 이 규율이 "docs가 커져서 AI가 못 읽고 환각"을 막는다. **docs를 읽을 땐 전체가 아니라 카드가 가리키는 정본 경로의 관련 절만** 읽어라(grep).
- 요구사항 변경은 **docs 수정에서 출발**한다 — 영향 분석·카드 정리는 `/change` 로
- 기능 제거 순서: **플래그 off → 코드 제거(라우트·화면·테스트·플래그 전부) → 스키마 drop은 마지막**(사용 0 확인 후 별도 마이그레이션). docs 절은 지우지 말고 "Removed(날짜·사유)" 표시
- 카드 여러 장짜리 미완성 기능은 **flags 파일로 메뉴·라우트를 가린다.** 규칙 세 줄:
  ①플래그 생성 시 **제거 카드를 동시 발행**하고, 플래그 해제(키 삭제)·프리뷰 제거는 **그 제거 카드에서만** 한다 — 마지막 기능 카드는 제거 카드를 의존으로 갖는다 (해제 지점을 두 카드에 적지 마라)
  ②플래그 뒤 기능의 검수 방법 = **표준 프리뷰 규약 `?preview={플래그명}`** (요청 단위로 플래그를 켜서 봄 — 앱 골격이 제공, Day 1) — 카드 "검수 방법" 칸에 이 URL을 적는다. 검수자는 여전히 브라우저만으로 검수한다
  ③시드 데이터가 필요한 기능이면 검수 방법에 **"재시드 필요"** 를 함께 표기 (검수 서버 재시드는 공통 개발자 담당)
- 되돌리기 어려운 설계 결정은 **처음 정할 때도, 바꿀 때도** `docs/adr/`에 ADR (바꿀 땐 새 파일 — 옛것엔 "대체됨 → 새 번호" 표시, 수정 금지) — 이 기록이 없으면 네가 옛 방향으로 "복원"하는 사고를 낸다. 채번·파일명은 템플릿 머리 참조. **ADR을 조회·작성할 땐 `docs/adr/INDEX.md`(현행 결정 목록)를 먼저 보고 같은 커밋에서 갱신한다** — 전체 grep은 대체된 옛 결정까지 걸린다

## 금지
- main 직접 push (유일 예외: **카드 #1로 추적되는 최초 구축·팀 태우기 커밋들** — 공통 개발자 가이드 절차) / 머지된 마이그레이션 수정 / package-lock 수동 편집
  (lock 충돌 시: package.json 만 해결 후 `npm install --package-lock-only`)
- **force push 금지**(`git push -f`·`--force`·`--force-with-lease` — 이력 파괴, 되돌리기 어렵다). settings.json deny가 막지만 **접두 규칙이라 체이닝(`git status && git push -f`)은 못 막는다**(실측) — 어느 형태든 force push는 하지 마라. main이 잘못됐으면 force가 아니라 **revert 커밋**으로 되돌린다
- **화면 동작 확인(렌더·클릭 왕복) 없이 검수요청으로 전환하기** (테스트 통과 ≠ 동작함 — 순서는 /done 이 강제한다)
- **"없다·안 켜져 있다·구판이다"를 직접 조회 없이 단정하기** — grep 0건·서브에이전트 요약·플레이스홀더 빈칸은 부재의 근거가 아니다(패턴 오류·기록 누락·추론일 수 있다 — 2026-07-29 하루 4회 실측). 부재를 주장하려면 **그 파일을 연 결과나 그 API를 호출한 결과**를 근거로 대라
