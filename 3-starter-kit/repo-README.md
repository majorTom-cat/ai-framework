## 2. 역할별 — 시작하는 법 + 하는 일

### 👩‍💻 개발자
- **처음 한 번**: repo clone → 폴더에서 `claude` → **`/start`** — **셋업 명령은 AI가 대신 실행합니다**(의존성 설치·앱 기동·개인 설정 파일). 당신은 알려주는 **확인 주소를 브라우저로 열기만** 하면 됩니다. 직접 해야 하는 건 **설치 프로그램(Docker Desktop 등)과 계정 로그인**뿐 (상세는 ONBOARDING)
- **매일 하는 일**: 내 모듈 카드를 위에서부터 — `/todo`(고르기) → `/dev`(개발)·`/fix`(수정) → `/done`(마무리) → **배포 화면 직접 확인**
- 공통(shared) 건드리면 **채팅 공지 먼저**
- 다른 모듈 기능 필요하면 소유자에게 `/card`
- **카드 없는 코드 변경 ❌**

### 📘 기획·디자이너 (비개발자)
- **처음 한 번**: **웹(GitLab — 설치 없음, 기본)** 또는 **Claude Code(선택 — 설치 필요, 별책 가이드)** — 각 가이드가 클릭 단위로 안내
- **하는 일**: 요구사항·시안 문서를 `docs/`에 **직접 올리고 고침** / 할 일·요구를 **카드로 등록** / 내게 배정된 **검수 카드 확인 → 닫기**
- 쓰는 스킬은 **`/start` · `/docs` · `/card`** 셋이면 충분

### 🛡️ 공통 개발자
- **처음(첫 주)**: 골격 구축 Day 0~6 (공통 개발자 가이드) — 팀이 올라탈 레일 깔기
- **그 뒤 하는 일**: 하루 10분 — main(팀의 공식 최신 코드) 상태·보드 대기열·검수 적체 확인 + 사건 대응 / **카드가 마르지 않게** 기획자와 이슈 비축

### 🧐 검수 담당 (전담자 없음 — 카드마다 배정)
- 내게 "검수" 배정된 카드를 **검수 서버에서 직접 써보고** 3기준(카드 기대대로 · 모바일 · 이상 입력 — 절차 정본은 [GitLab 가이드 §5](docs/00_Guide/AI_Working_Framework_Guide_GitLab.md#5-검수--배정받은-사람이-확인하고-완료-처리하는-법)) 확인 → 이상 없으면 **닫기**, 문제면 **반려**(진행중으로 되돌림)

## 3. 어떻게 작업하나 — 진행 순서

> 일은 **"카드"(= GitLab 이슈)** 단위로 움직입니다.
> **외울 명령은 사실상 `/start` 하나** — AI가 매번 응답 끝에 **`▶ 다음: /명령`** 으로 **다음에 할 수 있는 걸 선택지로** 띄워줘요. 당신은 그걸 **고르면** 됩니다. (자유롭게 타이핑하는 건 *고칠 내용을 말하거나 질문할 때만*.)
> 💬 **자연어로 "이거 해줘" 하고 시켜도 괜찮아요** — AI가 "그건 `/dev 12`로 하시면 됩니다"처럼 **맞는 스킬로 안내**해줍니다(그래야 팀 전원이 같은 절차 — 테스트·리뷰·검수 — 를 탑니다).

**개발자가 카드를 처리하는 순서:**

**◇ 내 모듈(기능 영역)을 처음 시작할 때 — 그 영역당 딱 한 번**
- **`/module 내모듈이름`** — 본보기와 같은 구조의 **빈 모듈 뼈대**가 생깁니다.
  (예: 게시판을 맡았으면 `/module board`. 모듈이 이미 있으면 이 단계는 건너뜀 — 바로 아래로.)

**◇ 그다음, 카드 하나하나 (매일의 반복)**
1. **`/todo`** — 내 카드를 **번호와 함께** 확인 (예: `12`번)
2. **`/dev 12`** — AI가 **두 번만** 확인을 구하고(①카드 이해가 맞는지 ②작업 계획대로 갈지) 나머지는 자동: 구현 → 테스트 → *(화면이면 UI 다듬기·검사)* → 저장. 끝나면 **`▶ 다음: /done 12`** 가 뜹니다 (상세 절차는 ONBOARDING)
3. **`/done 12`** — 테스트 → 코드 점검(민감하면 보안 점검) → 합치기 → **검수 서버 배포** → 검수 요청까지 자동
4. **검수 담당**이 배포된 화면을 직접 써보고, 이상 없으면 카드를 닫아요(완료)

> 💡 **작은 수정·버그·검수 반려**는 `/dev` 대신 **`/fix 12`** (물어보는 절차 없이 바로).
> 💡 `/ui`(화면 다듬기)·`/inspect`(화면 검사)는 **보통 `/dev`가 알아서** 부르지만, 화면만 다시 손보고 싶을 땐 **직접 `/ui 12`·`/inspect 12`** 로도 됩니다.

### 카드 번호(`#12`)는 어디서 보나?
- 🌐 **웹 (누구나)**: GitLab 왼쪽 **Plan → Issues**(목록) 또는 **Plan → Issue boards**(칸반 보드). 각 카드에 `#12`.
- 👩‍💻 **개발자 (터미널)**: **`/todo`** 를 치면 — 내가 할 카드를 **번호와 함께** 보여줍니다.

## 4. 스킬 — 하나씩

> 대부분은 **당신이 직접 부르고**, `/ui`·`/inspect`처럼 **`/dev`가 자동으로 부르는 것**도 있어요(직접 안 쳐도 되고, 필요하면 직접도 가능).

> **결과 표기** — 💬 채팅에만(파일·저장소는 안 바뀜) · 📄 repo 파일 · 🔀 git 커밋/머지 · 🦊 GitLab(이슈·라벨·설정) · 🚀 검수서버 배포
> 🔤 커밋=저장 · 머지=합치기 · MR=합쳐달라는 요청 (자세히는 GitLab 가이드 §0)

| | `/todo` | `/todo` | 💬 내 카드·멘션 목록(번호와 함께) (안 바뀜) | 세션 시작 / 개발자 |

> 상세 절차는 [ONBOARDING](docs/00_Guide/ONBOARDING.md). 각 스킬은 **부르면 그다음 순서를 알려주니** 외울 필요가 없어요. (`/`를 눌렀을 때 목록이 짧아 보여도 정상 — 몇 줄씩 보여주는 스크롤 목록이라 **한두 글자 이어 치면 필터링**됩니다: `/d` → /dev·/done. 자연어로 시켜도 AI가 맞는 스킬로 안내해요.) 그리고 **카드·댓글·머지처럼 바깥에 남는 것은 만들기 직전 "이렇게 남길게요" 미리보기를 보여주고 OK를 받아요** — 확인하다 보면 프로젝트가 어떻게 굴러가는지 자연스럽게 익습니다.

### Claude Code 내장 스킬 — 이 팀 흐름과 잘 맞는 것만 (개발자용)

위 표는 이 프로젝트 전용 스킬이고, Claude Code에 기본 탑재된 내장 스킬 중 아래는 함께 쓰면 좋다:

| 내장 스킬 | 언제 |
| --- | --- |
| `/code-review` | 작업 **중간에** 수시 셀프 리뷰 — /done을 기다릴 필요 없다 (/done 4단계의 fresh 리뷰는 별도로 자동) |
| `/run` 등 실행 계열 | 실앱을 띄워 변경 확인 — 증거 보강용 (화면 검사 정본은 `/inspect`) |
| 조사 계열(웹 검색 등) | 스택·라이브러리 등 **외부** 기술 조사 (검색 쿼리에 사내 정보·제품명 넣지 않기) — 세션·버전에 따라 이름이 다르다 |
| `/batch` | 대량 기계적 변경(전역 리네임·의존성 교체) — 카드·MR 규칙은 그대로 적용 |
| `/doctor` · `/debug` | Claude Code **자체**가 이상할 때 (프로젝트 문제가 아니라 도구 문제일 때) |

> 경계 두 가지: **장기 무인 실행(`/loop`·스케줄 등)에 개발을 위임하는 건 "알아서 해줘"와 같다** — 카드·`/dev`·`/fix` 흐름으로 (감시·조회 같은 읽기 전용 반복엔 써도 좋다). **아티팩트 발행·외부 서비스 업로드**(design-sync 등)는 사내 정보가 밖으로 나간다 — 하지 않는다.

## 5. 자주 있는 상황 — 이럴 땐?

> 개발하다 자주 부딪히는 것들. 외우지 말고 필요할 때 여기서 찾으세요.

| 상황 | 이렇게 |
| --- | --- |
| 자연어로 "이거 해줘" 하고 싶다 | 그냥 말해도 돼요 — AI가 "그건 `/dev 12`로요"처럼 **맞는 스킬로 안내**해줍니다 |
| **`/dev`·`/fix` 중 뭘 할지 모르겠다** | **큰 일(반나절 이상·새 화면·DB 구조·공통 코드)은 `/dev`, 작은 수정은 `/fix`.** 잘못 골라도 AI가 맞는 쪽으로 안내하니 아무거나로 시작해도 안전 |
| **다른 모듈/공통(shared)의 기능이 필요한데 없다** | 그 모듈을 **직접 고치지 말고** `/card`로 **소유자에게 요청**(원하는 함수 이름·입출력을 카드에 명시). shared 승격은 2개+ 모듈이 **실제로** 쓰거나 둘째 사용처 카드가 확정됐을 때만(미리 안 만듦) |
| **내가 공통(shared)·공용 파일을 고쳐야 한다** | 코드에 손대기 **전에 팀 채팅에 한 줄 공지**(허락이 아니라 알림). push(올리기) 때 "공용 파일을 바꿨습니다. 계속?" 확인창이 뜨면 내용 확인 후 진행 |
| 요구사항이 바뀌었다 | docs 정본을 고치고 → **`/change`** 로 영향받는 카드 정리 (비개발자는 docs 웹 편집 + 카드) |
| 검수에서 반려됐다 (카드가 진행중으로 돌아옴) | **`/fix 12`** — 반려 댓글이 곧 스펙 |
| 급한 요청·버그가 왔다 | 작은 건 **`/fix 12`**. 하던 걸 멈출지는 본인이 판단 |
| 개발하다 막혔다 | 먼저 **본보기 모듈**이 그걸 어떻게 했는지 본다 → 그래도 모호하면 **카드에 질문 댓글**(그 질문이 문서를 개선한다) |
| 이미 완료(Close)된 기능을 또 고쳐야 한다 | 옛 카드 재사용·Reopen ❌ → **새 카드 `(#12 후속)`** 로 등록 |
| 카드 없는 일을 하려 한다 | 먼저 **`/card 한 줄`** 로 카드부터 (카드 없는 코드 변경 ❌ — 나중에 아무도 이유를 모른다) |
| 큰 기능이라 여러 카드로 나눠 만든다 | 미완성이 검수 서버에 보이지 않게 **기능 플래그(flags)** 뒤에서 개발 (AI가 제거 카드까지 챙겨줌) |
| 머지된 변경이 잘못됐다 / main이 이상하다 | **되돌리기(revert)가 만사 우선** — AI에게 "MR !번호 revert MR 만들어줘"(또는 `git revert <머지커밋>` 브랜치→MR). 규모가 크거나 확신 없으면 공통 개발자 호출 |

> 더 자세한 건 [ONBOARDING](docs/00_Guide/ONBOARDING.md)(개발자) · [GitLab 실전 가이드](docs/00_Guide/AI_Working_Framework_Guide_GitLab.md)(비개발자).
